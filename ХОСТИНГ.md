# Размещение «ПроКод» на сервере

Полное руководство по публикации проекта в интернете: от выбора хостинга до зелёного
замка в адресной строке, мониторинга и резервных копий.

Документ рассчитан на человека, который **впервые видит консоль Linux**. Каждая команда
объясняется: что она делает и что должно появиться в ответ. Копируйте блоки целиком,
заменяя плейсхолдеры (`YOUR_SERVER_IP`, `prokod.ru`, `deploy`) на свои значения.

> Адрес репозитория в примерах — `github.com/hhttppss/procode.git` — настоящий, это
> репозиторий проекта, его менять не нужно. Но если вы сделали форк или перенесли код
> в свой аккаунт, подставляйте свой адрес везде, где встречается `hhttppss/procode`.

> 💡 **Совет:** это справочник по деплою. Как проект устроен внутри, что он умеет и какие
> у него команды — в [README.md](README.md). Как запустить его на своём компьютере —
> в [ЗАПУСК.md](ЗАПУСК.md). Здесь описано только то, что касается сервера.

## Что это за проект (одним экраном)

Чтобы не гадать при выборе хостинга, вот технический паспорт:

| Параметр | Значение |
|---|---|
| Платформа | Node.js, модули CommonJS |
| Фреймворк | Express 4 (`express@^4.21.2`) |
| Точка входа | `server/index.js`, запуск `npm start` |
| Версия Node | `>=20 <21 \|\| >=22` (поле `engines` в `package.json`). Рекомендуется **22 LTS** |
| Зависимости в проде | ровно три: `express`, `compression`, `better-sqlite3` |
| Сборщик | Tailwind CSS 3 — **только devDependency**, на сервере не нужен |
| База данных | SQLite через `better-sqlite3`, файл `data/app.sqlite`, режим WAL |
| Запасное хранилище | `DATABASE_ENGINE=json` — обычные JSON-файлы в `data/` |
| Внешние сервисы | нет: ни Redis, ни очередей, ни почтового шлюза, ни S3 |
| Процессов | **строго один** (см. [раздел 3.7](#37-автозапуск-systemd)) |
| Порт по умолчанию | 3000 |
| Версия проекта | 1.0.0 |

Всё состояние школы — заявки, ученики, расписание, финансы, учётные записи — лежит
в папке `data/`. Это единственное, что нельзя потерять.

## 1. Выбор сервера (2026)

<a id="11-почему-именно-vps"></a>

### 1.1 Почему именно VPS, а не shared-хостинг и не Vercel

Это Node.js-приложение, которое **постоянно работает** и **пишет файлы на диск**.
Из этих двух свойств следует всё остальное.

**Почему не обычный (shared) хостинг с панелью и PHP.** Там за 150 ₽ в месяц вам дают
папку, куда можно положить файлы, и веб-сервер, который отдаёт их по HTTP. Запустить
собственный процесс, который живёт круглосуточно и слушает порт, там либо нельзя вовсе,
либо можно в урезанном «Node.js-режиме», где хостер сам решает, когда ваш процесс
перезапустить. Отдельная беда — `better-sqlite3`: это нативный модуль, его нужно собрать
компилятором под конкретную версию Node. На shared-хостинге компилятора обычно нет.

**Почему не Vercel, Netlify, Cloudflare Pages и подобные.** Это платформы для
serverless-функций: ваш код запускается на время одного запроса, а потом контейнер
уничтожается. Для проекта «ПроКод» это смертельно по трём причинам:

1. **Нет постоянного диска.** Файловая система там временная. Файл `data/app.sqlite`
   переживёт один запрос и исчезнет. Заявки, ученики, расписание, финансы — всё пропадёт.
   Папка `backups/` тоже не сохранится: `npm run backup` положит архив в никуда.
2. **Счётчики в памяти обнулятся.** Ограничители частоты (8 неудачных входов за 15 минут,
   5 заявок за 10 минут с одного IP) и счётчик неудачных попыток входа живут в оперативной
   памяти процесса — это прямо написано в разделе «Известные ограничения» README.
   В serverless каждый запрос может попасть в новый экземпляр, и защита от перебора
   пароля перестанет работать.
3. **Каждый экземпляр — своя копия SQLite.** Даже если бы диск сохранялся, параллельные
   экземпляры писали бы в разные файлы. Данные разъехались бы за первый час.

Тот же аргумент касается любого «автомасштабирования» и Kubernetes с несколькими репликами.
Проект спроектирован как **одно приложение на одном диске** — и для школы на несколько сотен
учеников это правильное решение, а не компромисс.

**Что подходит:**

- обычный VPS/VDS с root-доступом (Ubuntu, Debian) — основной сценарий, ему посвящён
  этот документ;
- выделенный сервер — избыточно, но работает;
- облачная виртуалка (Yandex Cloud Compute, Selectel, VK Cloud) с **постоянным диском** —
  подходит, стоит дороже VPS и настраивается так же;
- Docker/контейнер на VPS — подходит при условии, что `data/` и `backups/` вынесены
  в постоянный том (volume), а контейнер запущен в одном экземпляре. Готового Dockerfile
  в проекте нет — это не мешает, просто придётся написать самому.

<a id="12-сколько-ресурсов-нужно"></a>

### 1.2 Сколько ресурсов нужно

Проект лёгкий: три зависимости, никаких браузерных сборок в рантайме, никакого Java/Ruby,
база — файл на диске. Основную память ест сам Node (около 60–120 МБ) плюс кэш коллекций.

| | Минимум | Рекомендуется | Комфорт с запасом |
|---|---|---|---|
| CPU | 1 vCPU | **2 vCPU** | 2–4 vCPU |
| RAM | 1 ГБ (+ swap 1–2 ГБ) | **2 ГБ** | 4 ГБ |
| Диск | 10 ГБ SSD | **20–40 ГБ NVMe** | 40–80 ГБ NVMe |
| ОС | Ubuntu 22.04 / Debian 12 | **Ubuntu 24.04 LTS** | Ubuntu 24.04 LTS |
| Сеть | выделенный IPv4 | выделенный IPv4 | выделенный IPv4 |

Пояснения:

- **1 ГБ RAM реально хватает** для школы на ~200 учеников. Но при 1 ГБ обязательно сделайте
  [swap-файл](#28-swap-файл): без него сборка `better-sqlite3` из исходников (если prebuild
  не подойдёт) может упасть по нехватке памяти, и `npm ci` завершится с загадочной ошибкой
  «Killed».
- **2 vCPU** нужны не для нагрузки, а для комфорта: пока приложение отвечает, вторым ядром
  работает nginx, certbot и ваш бэкап. На одном ядре ежедневный `npm run backup` заметно
  притормозит сайт на десяток секунд.
- **Диск — только NVMe или SSD, никогда HDD.** SQLite при каждой записи вызывает `fsync`,
  чтобы данные гарантированно легли на диск. На HDD это единицы миллисекунд на операцию,
  и платформа начинает ощутимо «залипать» при сохранении расписания на месяц вперёд.
- **Сколько места займут данные.** База школы на 200 учеников с двухлетней историей —
  единицы, максимум десятки мегабайт. Основное место съедят: система (~3 ГБ),
  `node_modules` (~40 МБ), журналы systemd (по умолчанию до 10% диска) и папка `backups/`,
  которая **сама не чистится** — про ротацию см. [5.8](#58-резервное-копирование).
- **Выделенный IPv4 обязателен**: без него не выпустить сертификат Let's Encrypt
  и не привязать домен A-записью.

<a id="16-россия-или-заграница"></a>

### 1.6 Россия или заграница

> ⚠️ **Осторожно. Это не мелочь и не вкусовщина.** Если школа работает в России, ученики
> и родители в России, а домен в зоне `.ru` — **берите российский хостинг**. Четыре причины,
> и одна из них юридическая.

**1. 152-ФЗ «О персональных данных» — самое важное.**
В базе этого проекта лежат: ФИО ребёнка, его возраст, направление обучения, заметки
о поведении и здоровье (поле «особенности» в карточке ученика), ФИО родителей, их телефоны
и адреса электронной почты, история оплат. Это персональные данные, причём часть — данные
несовершеннолетних, а заметки о здоровье при неудачной формулировке можно трактовать
как специальную категорию.

Закон (ч. 5 ст. 18 152-ФЗ) требует, чтобы **запись, систематизация, накопление, хранение,
уточнение и извлечение персональных данных граждан РФ выполнялись в базах данных,
находящихся на территории России**. Хранение базы школы на сервере в Германии этому
требованию не отвечает. Штрафы за нарушение локализации в последние годы выросли
до сотен тысяч рублей для юрлиц при первом нарушении и до миллионов при повторном,
а с 2025 года действует отдельная статья за утечки.

Отдельно: как оператор персональных данных школа должна подать уведомление
в Роскомнадзор — [pd.rkn.gov.ru](https://pd.rkn.gov.ru/) — и иметь Политику обработки
персональных данных на сайте. В проекте страница `public/privacy.html` пока заглушка,
её нужно заполнить настоящим документом (см. чек-лист «Что заменить перед публикацией»
в [README](README.md)).

**2. Скорость до ваших пользователей.**
Пинг из Москвы до Франкфурта — 40–60 мс, до российского дата-центра — 3–15 мс. Само по себе
это не катастрофа, но каждый TLS-хендшейк и каждый запрос платформы к `/app/api/*`
умножается на эту задержку. Лендинг с зарубежного сервера ощутимо «думает» перед открытием,
а платформа, которая делает несколько запросов подряд, — заметно вязче. Плюс трансграничные
маршруты в последние годы нестабильны: у части российских провайдеров периодически
деградируют стыки с европейскими сетями.

**3. Оплата.**
Hetzner, DigitalOcean и Vultr не принимают карты российских банков. Остаются посредники
и криптовалюта. Схема хрупкая: сорвался платёж — сервер выключили, а на нём вся школа.
Для инфраструктуры, от которой зависит работа бизнеса, это неприемлемый риск.

**4. Поддержка и язык.**
С российским провайдером вы напишете в чат по-русски в три часа ночи и получите ответ.
С Hetzner — тикет на английском и ответ утром по немецкому времени.

**Когда зарубежный хостинг оправдан:** если школа зарегистрирована не в России, ученики
за рубежом, а персональных данных россиян в базе нет. Тогда Hetzner — отличный выбор.

<a id="17-на-что-смотреть-при-покупке"></a>

### 1.7 На что смотреть при покупке

Чек-лист, который стоит прогнать по странице тарифа **до** оплаты:

- [ ] **Тип диска.** Только `NVMe` или `SSD`. Слово `HDD` или «SATA» в описании — проходите
      мимо: SQLite чувствителен к скорости `fsync`.
- [ ] **Ядро выделенное или общее.** Ищите «гарантированная частота», «dedicated CPU»,
      «100% vCPU». Формулировки «до 20% ядра», «shared», «burstable» означают, что при
      нагрузке соседей ваш сайт замедлится.
- [ ] **Трафик.** У большинства российских провайдеров трафик безлимитный при скорости
      100–200 Мбит/с. У зарубежных — квота (Hetzner: 20 ТБ), сверх неё платно. Проекту
      «ПроКод» хватит любой квоты с огромным запасом, но проверьте, что за перерасход
      не отключают сервер.
- [ ] **Снапшоты и бэкапы у провайдера.** Снапшот — «фотография» всего диска, позволяет
      откатить сервер целиком. Стоит обычно 10–20% от цены тарифа. Берите — но помните:
      это **не замена** бэкапу приложения, см. [5.8](#58-резервное-копирование).
- [ ] **KVM-консоль** (она же VNC, «аварийный доступ»). Без неё неудачная правка
      `sshd_config` или `ufw` означает потерю сервера. Есть у всех приличных провайдеров —
      убедитесь, что есть и у вашего.
- [ ] **Панель управления**: перезагрузка, переустановка ОС, смена тарифа, просмотр графиков
      нагрузки. Проверьте, что можно **увеличить** тариф без переезда.
- [ ] **Тестовый период или возврат денег.** У многих российских провайдеров есть 3–7 дней
      теста или возврат при отказе в первые сутки. Разверните проект на тесте, прогоните
      [чек-лист приёмки](#7-чек-лист-приёмки), и только потом платите за год.
- [ ] **Локация дата-центра.** Для российской аудитории — Москва или Санкт-Петербург.
- [ ] **IPv4.** Тарифы «только IPv6» дешевле, но домен к ним привязать нормально не выйдет:
      значительная часть российских домашних провайдеров до сих пор без IPv6.
- [ ] **Оплата помесячно на старте.** Годовая оплата дешевле, но сначала убедитесь,
      что провайдер вам подходит.

## 2. Установка и настройка сервера

Дальше всё пишется в предположении **Ubuntu 24.04 LTS**. На Debian 12 команды те же,
кроме установки Node.js (там тоже работает NodeSource) — различия отмечены отдельно.

<a id="21-создание-vps"></a>

### 2.1 Создание VPS

В панели провайдера при заказе сервера вас спросят четыре вещи:

1. **Операционная система.** Выберите **Ubuntu 24.04 LTS** («чистый» образ, без панелей
   ISPmanager/cPanel и без «преднастроенного Node.js» — мы поставим свежий сами).
   Буквы LTS означают долгосрочную поддержку: обновления безопасности до 2029 года.
2. **Регион / дата-центр.** Москва или Санкт-Петербург для российской аудитории.
3. **Конфигурация.** Из [таблицы 1.2](#12-сколько-ресурсов-нужно).
4. **Доступ.** Здесь важный момент: почти везде предлагают либо «пароль root на почту»,
   либо «добавить SSH-ключ». **Выбирайте SSH-ключ** — как его сделать, в следующем пункте.
   Если ключа ещё нет, сделайте его до заказа сервера.

После оплаты через 1–3 минуты вы получите **IP-адрес** вида `203.0.113.25`. Дальше в тексте
он называется `YOUR_SERVER_IP`.

<a id="22-ssh-ключ-вместо-пароля"></a>

### 2.2 SSH-ключ вместо пароля

SSH-ключ — это пара файлов: секретный остаётся у вас, публичный кладётся на сервер.
Вход по ключу нельзя подобрать перебором, в отличие от пароля. Боты сканируют интернет
и стучатся в порт 22 круглосуточно — через час после запуска сервера в журнале будут
сотни попыток входа. С ключом они бессмысленны.

**Windows (PowerShell).** OpenSSH встроен в Windows 10/11, ничего ставить не нужно.
Откройте PowerShell и выполните:

```powershell
ssh-keygen -t ed25519 -C "prokod-deploy"
```

- `-t ed25519` — современный тип ключа: короткий и надёжный;
- `-C "prokod-deploy"` — комментарий, чтобы потом отличить ключ от других.

Программа спросит:

- **путь для сохранения** — нажмите Enter, ключ ляжет в `C:\Users\<Вы>\.ssh\id_ed25519`;
- **passphrase (пароль на сам ключ)** — можно задать, тогда при каждом подключении
  придётся его вводить. Для рабочего сервера лучше задать.

В ответ появится «картинка» из символов (`randomart`) — значит, ключ создан. Теперь
покажите **публичную** часть, её и надо отдать провайдеру:

```powershell
Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub
```

Вывод — одна длинная строка вида:

```
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... prokod-deploy
```

Скопируйте её целиком и вставьте в поле «SSH-ключ» при заказе сервера (или добавьте
в разделе «SSH-ключи» панели провайдера, а потом привяжите к серверу).

> ⚠️ **Осторожно:** файл **без** расширения `.pub` (`id_ed25519`) — секретный.
> Его никому не отправляют, не выкладывают в git и не копируют на сервер.

**Linux / macOS** — команда та же самая, публичный ключ смотрится через `cat ~/.ssh/id_ed25519.pub`.

<a id="23-первый-вход-и-обновление-системы"></a>

### 2.3 Первый вход и обновление системы

Подключитесь к серверу (в PowerShell, терминале macOS/Linux — везде одинаково):

```bash
ssh root@YOUR_SERVER_IP
```

Первый раз система спросит:

```
The authenticity of host '203.0.113.25' can't be established.
ED25519 key fingerprint is SHA256:...
Are you sure you want to continue connecting (yes/no/[fingerprint])?
```

Это нормально: ваш компьютер видит сервер впервые и запоминает его отпечаток. Напечатайте
`yes` и нажмите Enter. Дальше вы увидите приглашение вида `root@prokod:~#` — вы внутри.

Первым делом обновите систему:

```bash
apt update && apt full-upgrade -y
```

- `apt update` — скачивает свежие списки пакетов (сами пакеты ещё не ставит);
- `apt full-upgrade -y` — обновляет всё установленное, `-y` отвечает «да» на вопросы.

Займёт 1–3 минуты, в конце будет строка вида `X upgraded, Y newly installed`. Если система
попросит перезагрузку (`System restart required`) — перезагрузите:

```bash
reboot
```

Соединение оборвётся, это ожидаемо. Через 20–40 секунд подключитесь снова той же командой
`ssh root@YOUR_SERVER_IP`.

Заодно поставьте инструменты, которые понадобятся дальше:

```bash
apt install -y curl git ufw fail2ban unzip build-essential python3 ca-certificates
```

Что зачем:

| Пакет | Зачем |
|---|---|
| `curl` | скачивать файлы и проверять сайт из консоли |
| `git` | забирать код проекта из репозитория |
| `ufw` | простой файрвол |
| `fail2ban` | блокировка тех, кто подбирает пароли |
| `unzip` | распаковывать архивы бэкапов вручную |
| `build-essential`, `python3` | компилятор C++ и Python — **нужны, если для `better-sqlite3` не найдётся готовой сборки** под вашу версию Node (см. [3.4](#34-установка-зависимостей)) |
| `ca-certificates` | корневые сертификаты для HTTPS-запросов |

<a id="24-часовой-пояс"></a>

### 2.4 Часовой пояс

> ⚠️ **Осторожно:** это тот шаг, который забывают, а потом две недели удивляются, почему
> занятие, поставленное на 10:00, показывается в 07:00, а зарплата за август частично
> попала в июль.

Свежий VPS почти всегда живёт в **UTC**. Приложение считает «сегодня», «эту неделю»
и «этот месяц» в поясе процесса — от этого зависят цифры дашборда, подсветка текущего дня
в расписании и, главное, границы периодов начисления зарплаты (`server/domain/payroll.js`).
Разница с Москвой — три часа.

Пояс задаётся в двух местах, и нужны оба:

**1. Пояс операционной системы** — чтобы совпадали журналы, cron и время в письмах:

```bash
timedatectl set-timezone Europe/Moscow
timedatectl
```

Вторая команда покажет текущее состояние. Ожидаемый вывод:

```
               Local time: Sun 2026-08-09 14:32:10 MSK
           Universal time: Sun 2026-08-09 11:32:10 UTC
                Time zone: Europe/Moscow (MSK, +0300)
System clock synchronized: yes
              NTP service: active
```

Строка `System clock synchronized: yes` означает, что часы сами подтягиваются с серверов
точного времени — так и должно быть.

**2. Пояс приложения** — переменная `TZ` в файле `.env` (см. [3.5](#35-файл-env-для-продакшена)).
Приложение выставляет `process.env.TZ` из неё при старте (`server/config.js`), не полагаясь
на систему. Значение печатается при запуске сервера строкой `Часовой пояс: Europe/Moscow` —
это первое, что нужно проверить в журнале после деплоя.

Если школа не в Москве — подставьте свой пояс из базы IANA: `Asia/Yekaterinburg`,
`Asia/Novosibirsk`, `Asia/Vladivostok`. Полный список: `timedatectl list-timezones`.

<a id="25-пользователь-без-прав-root"></a>

### 2.5 Пользователь без прав root

Под `root` можно случайно снести систему одной опечаткой, а любая уязвимость в приложении
сразу становится полным контролем над сервером. Заведём обычного пользователя — назовём
его `deploy`, — от которого будет работать приложение.

```bash
adduser deploy
```

Команда спросит пароль (задайте сложный и сохраните в менеджере паролей — он понадобится
для `sudo`) и несколько необязательных полей: «Full Name», «Room Number» и прочее —
их можно пропустить, нажимая Enter. В конце подтвердите `Y`.

Дайте пользователю право выполнять административные команды через `sudo`:

```bash
usermod -aG sudo deploy
```

Скопируйте ему свой SSH-ключ, чтобы заходить сразу под `deploy`:

```bash
rsync --archive --chown=deploy:deploy ~/.ssh /home/deploy/
```

Команда копирует папку `~/.ssh` пользователя `root` (куда провайдер положил ваш публичный
ключ) в домашнюю папку `deploy` и сразу назначает правильного владельца.

**Проверьте вход, не закрывая текущее окно.** Откройте **второе** окно PowerShell/терминала:

```bash
ssh deploy@YOUR_SERVER_IP
```

Должно пустить без пароля, приглашение изменится на `deploy@prokod:~$`. Проверьте `sudo`:

```bash
sudo whoami
```

Введите пароль пользователя `deploy` — в ответ должно быть `root`. Значит, права есть.

> ⚠️ **Осторожно:** пока новый вход не проверен в отдельном окне, **не закрывайте** сессию
> root и не переходите к следующему пункту. Иначе есть шанс запереть себя снаружи.

<a id="26-закрываем-ssh"></a>

### 2.6 Закрываем SSH

Теперь запретим вход под root и вход по паролю — останется только вход по ключу
под `deploy`. Это отсекает 99% автоматических атак.

Откройте конфигурацию SSH-сервера:

```bash
sudo nano /etc/ssh/sshd_config
```

`nano` — простейший текстовый редактор. Управление: стрелки — перемещение,
`Ctrl+O` затем Enter — сохранить, `Ctrl+X` — выйти, `Ctrl+W` — поиск.

Найдите и приведите к такому виду четыре строки (если строка закомментирована знаком `#`,
уберите его):

```
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
KbdInteractiveAuthentication no
```

| Параметр | Что делает |
|---|---|
| `PermitRootLogin no` | вход под root по SSH запрещён |
| `PasswordAuthentication no` | вход по паролю запрещён, только ключ |
| `PubkeyAuthentication yes` | вход по ключу разрешён |
| `KbdInteractiveAuthentication no` | закрывает обходной путь через «интерактивный» ввод пароля |

> ⚠️ **Осторожно:** в Ubuntu 24.04 настройки могут переопределяться файлами в папке
> `/etc/ssh/sshd_config.d/`. Проверьте, что там нет `PasswordAuthentication yes`:
> `sudo grep -r "PasswordAuthentication" /etc/ssh/sshd_config.d/`. Если есть —
> поправьте и там, иначе главный файл будет проигнорирован.

Проверьте синтаксис и примените:

```bash
sudo sshd -t && sudo systemctl restart ssh
```

`sshd -t` проверяет конфиг на ошибки. Если он молчит — ошибок нет, и `&&` запускает
перезапуск. Если ругается — исправьте, **не перезапуская** службу.

> ⚠️ **Осторожно:** сразу после перезапуска откройте **третье** окно и убедитесь, что
> `ssh deploy@YOUR_SERVER_IP` по-прежнему работает. Только после этого закрывайте старые
> сессии. Если доступ всё же потерян — заходите через KVM-консоль в панели провайдера.

Чтобы сервер сам ставил исправления уязвимостей:

```bash
sudo apt install -y unattended-upgrades

```

Вторая команда покажет синее окно с вопросом «Automatically download and install stable

<a id="28-swap-файл"></a>

### 2.8 Swap-файл

Swap — файл на диске, который система использует как «запасную» оперативную память.
На сервере с 1 ГБ RAM он обязателен: без него `npm ci` при сборке `better-sqlite3`
из исходников может быть убит системой (в журнале появится `Killed`), а при всплеске
нагрузки OOM-killer прибьёт само приложение.

Создать swap на 2 ГБ:

```bash
sudo fallocate -l 2G /swapfile          # создать файл нужного размера
sudo chmod 600 /swapfile                # доступ только root — там может оказаться что угодно из памяти
sudo mkswap /swapfile                   # разметить файл как область подкачки
sudo swapon /swapfile                   # включить прямо сейчас
```

Чтобы swap включался после перезагрузки, допишите строку в таблицу файловых систем:

```bash
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

Проверка:

```bash
free -h
```

Ожидаемый вывод — строка `Swap:` с ненулевым размером:

```
               total        used        free      shared  buff/cache   available
Mem:           1.9Gi       220Mi       1.2Gi       1.0Mi       500Mi       1.5Gi
Swap:          2.0Gi          0B       2.0Gi
```

> 💡 **Совет:** если RAM 2 ГБ и больше, swap всё равно полезен как страховка,
> но можно ограничиться 1 ГБ. Заодно уменьшите «желание» системы уходить в swap:
> `sudo sysctl vm.swappiness=10` и строка `vm.swappiness=10` в `/etc/sysctl.conf`.

<a id="29-fail2ban"></a>

### 2.9 fail2ban

`fail2ban` читает журналы и временно блокирует IP-адреса, с которых идёт подбор пароля.
Пакет уже установлен в [2.3](#23-первый-вход-и-обновление-системы), осталось настроить.

Создайте свой файл настроек (штатный `jail.conf` не редактируют — он перезапишется
при обновлении):

```bash
sudo nano /etc/fail2ban/jail.local
```

Вставьте:

```ini
[DEFAULT]
# Сколько держать в бане. 1h — час; -1 означает «навсегда»
bantime  = 1h
# За какой период считать неудачные попытки
findtime = 10m
# Сколько попыток допустимо до бана
maxretry = 5
# Никогда не банить свои адреса (подставьте свой домашний IP, если он статический)
ignoreip = 127.0.0.1/8 ::1

[sshd]
enabled = true
```

Сохраните (`Ctrl+O`, Enter, `Ctrl+X`) и перезапустите:

```bash
sudo systemctl restart fail2ban
sudo fail2ban-client status sshd
```

Последняя команда покажет статистику:

```
Status for the jail: sshd
|- Filter
|  |- Currently failed: 0
|  |- Total failed:     43
|  `- File list:        /var/log/auth.log
`- Actions
   |- Currently banned: 2
   `- Total banned:     7
```

Цифры `Total failed` и `Total banned` вырастут за первые же сутки — это нормальный фоновый
шум интернета. Настройка fail2ban для nginx — в [5.4](#54-fail2ban-для-nginx).

<a id="210-установка-nodejs-22-lts"></a>

### 2.10 Установка Node.js 22 LTS

В `package.json` проекта указано `"node": ">=20 <21 || >=22"`. То есть подходят версии
**20** и **22 и новее**, а версия 21 исключена намеренно (это была нестабильная
«нечётная» ветка). Рекомендуется **Node.js 22 LTS**: у него длинная поддержка
и под него точно есть готовые сборки `better-sqlite3`.

> ⚠️ **Осторожно:** не гонитесь за самой свежей версией Node. `better-sqlite3` — нативный
> модуль; для каждой версии Node нужен свой скомпилированный бинарник. Если вы поставите
> версию, вышедшую вчера, готового бинарника («prebuild») для неё может не быть, и npm
> полезет собирать модуль из исходников — что требует компилятора, времени и памяти,
> а на слабой машине иногда просто падает. Node 22 LTS — безопасный выбор.

**Вариант А: NodeSource (рекомендуется для сервера).**

Node ставится как системный пакет, обновляется вместе с системой, доступен всем
пользователям и всем службам — а значит, systemd-юниту не придётся искать node
в чужом домашнем каталоге.

```bash
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs
```

Первая строка скачивает установочный скрипт NodeSource и добавляет их репозиторий
в систему; вторая ставит сам Node. Проверьте:

```bash
node -v    # ожидается v22.x.x
npm -v     # ожидается 10.x.x или новее
which node # ожидается /usr/bin/node
```

Запомните путь `/usr/bin/node` — он понадобится в systemd-юните.

**Вариант Б: nvm (менеджер версий).**

Подходит, если на одном сервере живёт несколько проектов на разных версиях Node или
вы хотите быстро переключаться между версиями для проверки. Ставится **под конкретного
пользователя**, не системно.

```bash
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash
source ~/.bashrc
nvm install 22
nvm alias default 22
node -v
```

> ⚠️ **Осторожно:** с nvm путь до node выглядит как
> `/home/deploy/.nvm/versions/node/v22.x.x/bin/node` и меняется при каждом обновлении
> версии. systemd не читает `~/.bashrc`, поэтому в юните и в cron нужно указывать
> **полный путь** — и не забывать править его после `nvm install`. Именно из-за этого
> для одного проекта на сервере проще NodeSource.

**Как проверить, какой вариант у вас уже стоит:** `which -a node` покажет все найденные
пути. Если там и `/usr/bin/node`, и что-то из `.nvm` — вы получите разные версии в разных
контекстах, и это источник трудноуловимых ошибок. Оставьте что-то одно.

Официальная документация: [nodejs.org](https://nodejs.org/),
[github.com/nodesource/distributions](https://github.com/nodesource/distributions),
[github.com/nvm-sh/nvm](https://github.com/nvm-sh/nvm).

<a id="211-sqlite-что-ставить-а-что-не-нужно"></a>

### 2.11 SQLite: что ставить, а что не нужно

Частое недоразумение: «раз база SQLite, надо поставить SQLite».

**Для работы приложения отдельный SQLite не нужен.** Пакет `better-sqlite3` содержит
внутри себя полноценный движок SQLite, скомпилированный в нативный модуль Node. Он
не вызывает системный `sqlite3` и не зависит от него. Поставили `npm ci` — база работает.

**Консольная утилита `sqlite3` полезна** — но только вам, для ручных запросов
к базе, диагностики и альтернативных способов бэкапа:

```bash
sudo apt install -y sqlite3
sqlite3 --version    # например: 3.45.1 2024-01-30 ...
```

Пример использования (сервер при чтении останавливать не обязательно):

```bash
cd /srv/prokod
sqlite3 data/app.sqlite ".tables"                       # какие таблицы есть
sqlite3 data/app.sqlite "SELECT COUNT(*) FROM students;" # сколько учеников
sqlite3 data/app.sqlite "PRAGMA integrity_check;"        # проверка целостности, ожидается ok
sqlite3 data/app.sqlite "PRAGMA journal_mode;"           # ожидается wal
```

> ⚠️ **Осторожно:** **не выполняйте изменяющие запросы** (`UPDATE`, `DELETE`, `INSERT`)
> к рабочей базе при запущенном сервере. Приложение держит свой кэш коллекций
> (`server/db.js`) и не узнает о правках извне, а согласованность данных между
> коллекциями ему обеспечивают транзакции, о которых ваш ручной запрос не знает.
> Нужно что-то поправить руками — остановите службу, сделайте бэкап, правьте, запускайте.

Про режим WAL, который использует база, — [sqlite.org/wal.html](https://sqlite.org/wal.html).
Он важен для понимания бэкапов, см. [6.3](#63-три-способа-снять-копию-базы).

## 3. Настройка проекта на сервере

<a id="31-куда-класть-проект"></a>

### 3.1 Куда класть проект

Общепринятых мест два: `/srv/prokod` (по стандарту FHS `/srv` — данные, которые сервер
отдаёт наружу) и `/var/www/prokod` (историческое место веб-проектов). Разницы по существу
нет. В документе используется **`/srv/prokod`**.

```bash
sudo mkdir -p /srv/prokod
sudo chown deploy:deploy /srv/prokod
```

- `mkdir -p` создаёт папку (и родительские, если их нет);
- `chown deploy:deploy` делает владельцем пользователя `deploy` — от него будет
  работать приложение, и оно должно иметь право писать в `data/` и `backups/`.

> ⚠️ **Осторожно:** не разворачивайте проект в `/root` и не запускайте его от `root`.
> Приложение принимает запросы из интернета — оно должно работать с минимальными правами.

<a id="32-заливка-кода-git-через-deploy-key"></a>

### 3.2 Заливка кода: git через deploy key

Самый удобный способ: сервер сам забирает код из GitHub, обновление — одна команда
`git pull`. Deploy key — это SSH-ключ, привязанный к **одному репозиторию**, с правом
только на чтение. Даже если сервер взломают, злоумышленник не получит доступ к остальным
вашим репозиториям.

**Шаг 1. Создать ключ на сервере** (под пользователем `deploy`):

```bash
ssh-keygen -t ed25519 -C "prokod-server-deploy" -f ~/.ssh/id_ed25519_prokod -N ""
```

- `-f` — куда сохранить (отдельный файл, чтобы не смешивать с личными ключами);
- `-N ""` — без passphrase: сервер должен уметь подтягивать код без участия человека.

**Шаг 2. Показать публичную часть:**

```bash
cat ~/.ssh/id_ed25519_prokod.pub
```

Скопируйте всю строку (`ssh-ed25519 AAAA... prokod-server-deploy`).

**Шаг 3. Добавить ключ в GitHub.** Откройте репозиторий → **Settings** → **Deploy keys** →
**Add deploy key**:

- **Title**: `prokod production server`;
- **Key**: вставьте скопированную строку;
- **Allow write access**: **не включайте** — серверу нужно только читать.

**Шаг 4. Объяснить SSH, каким ключом ходить в GitHub:**

```bash
nano ~/.ssh/config
```

Содержимое:

```
Host github.com
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519_prokod
  IdentitiesOnly yes
```

Права на файл конфигурации должны быть строгими, иначе SSH его проигнорирует:

```bash
chmod 600 ~/.ssh/config
```

**Шаг 5. Проверить связь:**

```bash
ssh -T git@github.com
```

Ожидаемый ответ:

```
Hi hhttppss/procode! You've successfully authenticated, but GitHub does not provide shell access.
```

Фраза «does not provide shell access» — это **успех**, а не ошибка.

**Шаг 6. Забрать код:**

```bash
git clone git@github.com:hhttppss/procode.git /srv/prokod
cd /srv/prokod
ls
```

В листинге должны быть `server/`, `public/`, `scripts/`, `package.json`, `README.md`.

> 💡 **Совет:** папок `data/` и `backups/` после клонирования **не будет** — они
> в `.gitignore` (там рабочие данные и копии). Приложение и скрипты создают их сами
> при первом запуске. Если используете systemd с `ProtectSystem=strict`, создайте их
> заранее руками — см. [3.7](#37-автозапуск-systemd).

**Что ещё не приедет из git и почему это важно:**

| Не в репозитории | Последствие | Что делать |
|---|---|---|
| `.env` | сервер стартует со случайным секретом сессии и стандартным паролем | создать вручную, [3.5](#35-файл-env-для-продакшена) |
| `data/*.sqlite`, `data/*.json` | база пустая, сотрудников нет | `npm run seed:reset` или `npm run user:add`, [3.6](#36-первый-запуск-и-учётные-записи) |
| `backups/` | нет копий | настроить cron, [5.8](#58-резервное-копирование) |
| `node_modules/` | нет зависимостей | `npm ci --omit=dev`, [3.4](#34-установка-зависимостей) |

А вот **`public/css/styles.css` в репозитории есть** — собранный Tailwind закоммичен.
Это ключевая деталь, из-за неё на сервере не нужен ни Tailwind, ни devDependencies.
Подробно — в следующих двух пунктах.

<a id="33-заливка-кода-без-github-scp-и-rsync"></a>

### 3.3 Заливка кода без GitHub: scp и rsync

Если репозитория нет или пользоваться git не хочется, файлы можно скопировать напрямую.

**rsync (рекомендуется).** Копирует только изменившееся, умеет исключать папки.
На Windows доступен в Git Bash или WSL:

```bash
rsync -avz --delete \
  --exclude 'node_modules' \
  --exclude '.git' \
  --exclude 'data' \
  --exclude 'backups' \
  --exclude '.env' \
  --exclude 'ЗАПУСК.md' \
  /d/ProCode/ deploy@YOUR_SERVER_IP:/srv/prokod/
```

- `-a` — сохранять права и структуру, `-v` — показывать что делает, `-z` — сжимать в пути;
- `--delete` — удалять на сервере то, чего больше нет локально (иначе накопится мусор);
- `--exclude` — **обязательно** исключите `data`, `backups` и `.env`: иначе вы затрёте
  рабочую базу школы своей локальной и перезапишете серверные секреты.

> ⚠️ **Осторожно:** обратите внимание на **завершающий слэш** в `/d/ProCode/`. Без него
> rsync создаст `/srv/prokod/ProCode/`. Это классическая ловушка.

**scp (проще, но копирует всё целиком).** Из PowerShell:

```powershell
scp -r D:\ProCode\* deploy@YOUR_SERVER_IP:/srv/prokod/
```

После этого удалите с сервера лишнее (`node_modules`, если случайно уехало) и убедитесь,
что локальный `.env` не перезаписал серверный.

> 💡 **Совет:** при копировании файлов вручную легко забыть пересобрать CSS перед отправкой.
> Локально выполняйте `npm run css` **до** заливки, если правили разметку или классы.

<a id="34-установка-зависимостей"></a>

### 3.4 Установка зависимостей

```bash
cd /srv/prokod
npm ci --omit=dev
```

**Что означает каждая часть:**

- **`npm ci`** вместо `npm install` — «clean install». Ставит зависимости **строго**
  по `package-lock.json`, не меняя его, предварительно удалив `node_modules` целиком.
  Это гарантирует, что на сервере окажутся ровно те версии, что вы проверили локально.
  `npm install` в тех же условиях может подтянуть более свежую минорную версию
  и переписать lock-файл — на боевом сервере это лишний источник сюрпризов.
- **`--omit=dev`** — не ставить devDependencies. В проекте devDependency ровно одна —
  `tailwindcss`, и на сервере она не нужна.

Итого установятся три пакета и их зависимости: `express`, `compression`, `better-sqlite3`.
Займёт 20–60 секунд.

**Почему `npm run css` на сервере запускать НЕ нужно.**

Файл `public/css/styles.css` (собранный Tailwind) **закоммичен в репозиторий** — проверяется
командой `git ls-files public/css/`, она выводит `public/css/styles.css`. То есть готовые
стили приезжают вместе с кодом.

> ⚠️ **Осторожно, противоречие в README.** В разделе «Публикация на сервере» файла
> [README.md](README.md) написано: «выполните `npm install --omit=dev` и `npm run css`».
> Эти две команды несовместимы: `--omit=dev` не ставит `tailwindcss`, и `npm run css`
> тут же упадёт с `tailwindcss: not found`. Правильный порядок такой:
>
> 1. **Локально**, на машине разработчика: правите разметку или классы → `npm run css` →
>    коммит изменённого `public/css/styles.css` → `git push`.
> 2. **На сервере**: `git pull` → `npm ci --omit=dev` → перезапуск службы. Никакого
>    Tailwind на сервере.
>
> Если вы всё же хотите собирать CSS на сервере (например, заливаете код через rsync
> без git), ставьте зависимости **без** `--omit=dev` (`npm ci`) и тогда запускайте
> `npm run css`. Это медленнее и тянет на боевой сервер лишние 30+ МБ пакетов сборки.

**Если `better-sqlite3` не установился.**

Это нативный модуль: внутри — движок SQLite на C, который должен быть скомпилирован под
вашу связку «версия Node + операционная система + архитектура». Обычно npm скачивает
готовый бинарник (prebuild) и всё проходит незаметно. Проблемы бывают в трёх случаях:

| Ситуация | Что происходит | Решение |
|---|---|---|
| Слишком свежая версия Node | prebuild ещё не выпущен, npm собирает из исходников | нужны `build-essential` и `python3` (ставили в [2.3](#23-первый-вход-и-обновление-системы)); лучше — поставить Node 22 LTS |
| Alpine Linux / musl (обычно в Docker) | prebuild собран под glibc и не подходит | ставить `apk add --no-cache python3 make g++` и собирать из исходников, либо взять образ `node:22-bookworm-slim` вместо `node:22-alpine` |
| Экзотическая архитектура | prebuild отсутствует | сборка из исходников |
| Мало памяти при сборке | процесс убит: `Killed` | [swap-файл](#28-swap-файл) |

Диагностика — сборка с подробным выводом:

```bash
npm ci --omit=dev --foreground-scripts
```

Проверить, что модуль реально работает:

```bash
node -e "const db=require('better-sqlite3')(':memory:'); console.log('better-sqlite3 OK', db.prepare('select sqlite_version() v').get());"
```

Ожидается что-то вроде `better-sqlite3 OK { v: '3.50.4' }`.

**Запасной вариант, если собрать так и не удалось.** В проекте есть второй движок хранения —
обычные JSON-файлы. Он описан в `.env.example` именно как страховка «если на сервере
не собирается нативный драйвер `better-sqlite3`». Поставьте в `.env`:

```ini
DATABASE_ENGINE=json
```

Приложение будет работать полностью — интерфейс и API одинаковы, — но с одной оговоркой
из README: транзакции по нескольким коллекциям в JSON-режиме атомарны только на уровне
одного файла за раз. Это рабочий временный режим, а не постоянное решение. Когда
`better-sqlite3` заработает, перенесите данные: `npm run migrate:sqlite`, затем верните
`DATABASE_ENGINE=sqlite`. Исходные JSON-файлы миграция не трогает — они останутся
как страховка.

Документация модуля: [github.com/WiseLibs/better-sqlite3](https://github.com/WiseLibs/better-sqlite3).

<a id="35-файл-env-для-продакшена"></a>

### 3.5 Файл .env для продакшена

Файл `.env` в репозиторий не попадает (он в `.gitignore`), поэтому его создают на сервере
руками. Возьмите за основу `.env.example` из проекта.

**Сначала сгенерируйте секрет сессии:**

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Команда напечатает 64 шестнадцатеричных символа, например:
`a3f1c8e0b47d92...`. Скопируйте — сейчас вставим.

**Создайте файл:**

```bash
cd /srv/prokod
nano .env
```

**Готовое содержимое для продакшена** (замените значения в угловых скобках):

```ini
# ── Сеть ───────────────────────────────────────────────────────────────────
# Порт, на котором работает Node. Наружу он не смотрит: перед ним стоит nginx,
# а сам порт закрыт файрволом. Менять смысла нет, если 3000 ничем не занят.
PORT=3000

# ── Запасной вход ──────────────────────────────────────────────────────────
# Работает, ТОЛЬКО пока не заведён ни один сотрудник. Как только появился
# первый пользователь, эта пара логин/пароль перестаёт действовать.
# Всё равно задайте свои значения: они понадобятся, если файл учётных
# записей будет потерян и в систему станет некому войти.
ADMIN_LOGIN=<ваш-логин>
ADMIN_PASSWORD=<длинный-пароль-не-procode2025>

# ── Секрет сессии ──────────────────────────────────────────────────────────
# Подписывает cookie администратора. Вставьте вывод команды:
#   node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
# Если оставить пустым или значение-заглушку — сервер сгенерирует временный
# секрет при каждом старте, и после перезапуска ВСЕХ выбросит из платформы.
SESSION_SECRET=<64-символа-из-команды-выше>

# ── Часовой пояс ───────────────────────────────────────────────────────────
# От него зависят «сегодня» на дашборде, подсветка дня в расписании
# и границы периодов начисления зарплаты. VPS по умолчанию живёт в UTC —
# без этой строки всё уедет на три часа.
TZ=Europe/Moscow

# ── Хранилище ──────────────────────────────────────────────────────────────
# sqlite — рабочий режим. json — запасной, если не собрался better-sqlite3.
DATABASE_ENGINE=sqlite
SQLITE_STORAGE=data/app.sqlite

# ── Обратный прокси ────────────────────────────────────────────────────────
# ОБЯЗАТЕЛЬНО 1, если перед приложением стоит nginx или Caddy.
# Тогда Express берёт настоящий IP клиента из X-Forwarded-For.
# Если прокси НЕТ и Node смотрит в интернет напрямую — должно быть 0,
# иначе заголовок можно подделать и обойти ограничения по IP.
TRUST_PROXY=1
```

Сохраните (`Ctrl+O`, Enter, `Ctrl+X`) и **закройте файл от посторонних**:

```bash
chmod 600 /srv/prokod/.env
ls -l /srv/prokod/.env
```

Ожидается `-rw------- 1 deploy deploy` — читать и писать может только владелец.
В файле лежат пароль администратора и секрет сессии; права `644` означали бы, что его
прочтёт любой пользователь сервера.

**Разбор двух настроек, которые ломают проект чаще всего.**

> ⚠️ **`TRUST_PROXY` — самая коварная строка в этом файле.**
>
> Когда запрос идёт через nginx, Express видит адрес отправителя `127.0.0.1` — это сам
> nginx. Настоящий адрес посетителя прокси кладёт в заголовок `X-Forwarded-For`.
> При `TRUST_PROXY=1` Express берёт адрес оттуда.
>
> **Забыли поставить 1 за прокси:** все посетители выглядят как один клиент `127.0.0.1`.
> Ограничитель формы заявки (5 успешных заявок и 30 обращений за 10 минут с одного IP)
> сработает на шестом родителе за десять минут — **и заблокирует всех остальных**.
> То же с входом: восемь неудачных попыток любого сотрудника закроют вход **всей школе**
> на 15 минут. Симптом: «форма перестала отправляться», «никто не может войти»,
> при этом в журнале ничего страшного.
>
> **Поставили 1 без прокси** (Node смотрит в интернет напрямую): любой может прислать
> заголовок `X-Forwarded-For: 1.2.3.4`, менять его на каждом запросе — и ограничения
> по IP перестанут существовать вовсе. Перебор пароля станет возможен.
>
> Правило простое: **есть nginx/Caddy → 1, нет → 0.**

> 🔴 **Половина правды опаснее целой лжи: `TRUST_PROXY=1` с неправильным nginx.**
>
> Во многих руководствах по nginx заголовок передают так:
>
> ```nginx
> proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;   # ← ТАК НЕЛЬЗЯ
> ```
>
> Переменная `$proxy_add_x_forwarded_for` **не заменяет** заголовок, а **дописывает**
> адрес к тому, что уже прислал клиент. Если посетитель сам отправит
> `X-Forwarded-For: 1.2.3.4`, nginx превратит это в `1.2.3.4, <настоящий IP>`.
>
> А приложение при `TRUST_PROXY=1` выполняет `app.set('trust proxy', true)`
> (`server/index.js`) — Express в этом режиме доверяет **всей цепочке** и берёт
> **самое левое** значение. То есть `1.2.3.4`. Поддельное.
>
> Меняя заголовок на каждом запросе, атакующий получает «новый IP» каждый раз и
> обходит **все** ограничения сразу: блокировку перебора пароля (8 попыток за 15 минут),
> лимит заявок (5 за 10 минут) и лимиты внутреннего API. Снаружи всё выглядит здоровым:
> сайт работает, лимиты «срабатывают» при обычной проверке — защиты просто нет.
>
> **Правильно — передавать адрес, который видит сам nginx. Подделать его нельзя:**
>
> ```nginx
> proxy_set_header X-Forwarded-For $remote_addr;   # ← ТАК НАДО
> ```
>
> Во всех конфигах этого документа используется именно `$remote_addr`. Если вы берёте
> конфиг из другой статьи — проверьте эту строку первым делом.
>
> **Как проверить на живом сервере.** Отправьте запрос с подставным заголовком:
>
> ```bash
> curl -s -H 'X-Forwarded-For: 1.2.3.4' https://prokod.ru/ -o /dev/null -w '%{http_code}\n'
> ```
>
> Затем посмотрите журнал приложения: `sudo journalctl -u prokod -n 20`. Адрес `1.2.3.4`
> в записях появляться **не должен** — там должен быть ваш настоящий адрес.
>
> **Для Caddy** заголовки проставляются автоматически, и по умолчанию Caddy тоже
> дописывает к клиентскому значению. Если используете Caddy (раздел 3.11), задайте
> список доверенных прокси явно — см. документацию
> [`trusted_proxies`](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#trusted_proxies).
> Не уверены в настройке — надёжнее взять nginx с явной строкой выше.

> ⚠️ **`SESSION_SECRET`.** Если оставить заглушку `change-me-to-a-long-random-string`
> или удалить строку, `server/config.js` сгенерирует случайный секрет при старте
> и напечатает предупреждение. Формально всё работает, но каждый перезапуск (обновление,
> `systemctl restart`, автоматический рестарт после сбоя) делает все выданные cookie
> недействительными — сотрудники будут выбрасываться на страницу входа в случайные
> моменты. При настроенном `Restart=always` это выглядит как «платформа глючит».

### 3.6 Первый запуск и учётные записи

Прежде чем оформлять службу, проверьте, что приложение вообще стартует.

```bash
cd /srv/prokod
npm start
```

Ожидаемый вывод:

```
  ПроКод — сервер запущен
  Лендинг:    http://localhost:3000/
  Платформа:  http://localhost:3000/app
  Вход:       http://localhost:3000/login
  Часовой пояс: Europe/Moscow
  Стили:      npm run css — пересобрать CSS после правок разметки
```

**Проверьте строку «Часовой пояс»** — там должно быть `Europe/Moscow`, а не `UTC`.
Если ниже появился блок `⚠ ВНИМАНИЕ` — прочитайте его: там пишут про незаданный
`SESSION_SECRET` и про стандартный пароль. Оба замечания нужно устранить в `.env`.

В **другом** окне терминала проверьте, что сервер отвечает:

```bash
curl -I http://127.0.0.1:3000/
```

Ожидается `HTTP/1.1 200 OK` и заголовки `Content-Security-Policy`, `X-Frame-Options: DENY`,
`Cache-Control: no-cache`.

Вернитесь в первое окно и остановите сервер: `Ctrl + C`.

**Создание учётных записей.** База пустая, войти пока некому (кроме запасного входа
по `ADMIN_LOGIN`/`ADMIN_PASSWORD`, который отключится, как только появится первый
сотрудник). Есть два пути.

*Путь 1: чистая база для боевой работы* — только ваша учётная запись, никаких демо-данных:

```bash
cd /srv/prokod
npm run user:add -- <логин> <пароль>
```

Флаги ролей: без флага — администратор, `--manager` — управляющий школы,
`--teacher` — преподаватель. Например:

```bash
node scripts/manage-users.js --add director SuperPass2026 --name "Анна Иванова"
node scripts/manage-users.js --add manager1 OtherPass2026 --manager --name "Пётр Смирнов"
```

Чтобы пароль не попал в историю команд оболочки, передайте его через стандартный ввод:

```bash
echo "SuperPass2026" | node scripts/manage-users.js --add director
```

Проверить список: `npm run users`.

*Путь 2: демо-данные для показа и обучения* — заявки, ученики, расписание, финансы
и три демо-преподавателя:

```bash
npm run seed:reset
```

> ⚠️ **Осторожно:** `seed:reset` **очищает рабочие данные** (кроме учётных записей)
> и создаёт демо заново. На сервере, где уже идёт настоящая работа, эта команда сотрёт
> заявки, учеников, расписание и финансы. Запускайте только на пустой базе.
>
> И обязательно удалите демо-преподавателей (`orlova`, `kim`, `volkova`, пароль
> у всех `demo12345`) перед тем, как открыть сайт публике:
> `node scripts/manage-users.js --remove orlova` и так далее.

Подробнее про роли, флаги и поведение при удалении — в разделе «Учётные записи»
[README.md](README.md).

<a id="37-автозапуск-systemd"></a>

### 3.7 Автозапуск: systemd

Пока приложение запущено командой `npm start` в вашем терминале, оно умрёт, как только
вы закроете SSH-сессию. Нужна служба, которая стартует при загрузке сервера
и перезапускается после сбоя. Штатный механизм Linux для этого — systemd.

> ⚠️ **САМОЕ ВАЖНОЕ ПРЕДУПРЕЖДЕНИЕ ВО ВСЁМ ДОКУМЕНТЕ.**
>
> **Процесс приложения должен быть ровно один.** Никакого cluster-режима Node, никакого
> `pm2 start -i max`, никаких двух копий службы, никаких «двух серверов на одну базу»
> и никаких нескольких реплик в оркестраторе.
>
> Три независимые причины:
>
> 1. **`better-sqlite3` работает синхронно и держит файл базы.** Два процесса, пишущие
>    в один `app.sqlite`, регулярно упираются друг в друга: запросы падают с ошибкой
>    `SQLITE_BUSY: database is locked`. Режим WAL позволяет читать во время записи,
>    но одновременная запись из двух процессов всё равно сериализуется, а очередь
>    изменений в `server/db.js` координирует запросы **внутри одного процесса** —
>    про второй процесс она не знает.
> 2. **Счётчики ограничения частоты живут в памяти процесса.** При двух процессах
>    злоумышленник получает вдвое больше попыток подбора пароля, а честный посетитель
>    ловит блокировку непредсказуемо — балансировщик кидает его то в один процесс,
>    то в другой.
> 3. **Кэш коллекций тоже в памяти.** Второй процесс не узнает об изменениях, сделанных
>    первым. Пользователи начнут видеть разные данные в зависимости от того, куда попал
>    их запрос: «я сохранил ученика, обновил страницу — его нет, обновил ещё раз — есть».
>
> Проект рассчитан на школу в несколько сотен учеников, и одного процесса Node хватает
> с многократным запасом. Масштабировать здесь нечего — не пытайтесь.
>
> Быстрая проверка в любой момент: `ps aux | grep "[n]ode"` — должна быть **одна** строка
> с `server/index.js`.

**Создайте файл службы:**

```bash
sudo nano /etc/systemd/system/prokod.service
```

**Готовый unit-файл:**

```ini
[Unit]
Description=ProKod — сайт и платформа школы программирования
Documentation=file:///srv/prokod/README.md
# Стартовать после того, как поднялась сеть
After=network-online.target
Wants=network-online.target

[Service]
Type=simple

# ── Кто и откуда ───────────────────────────────────────────────────────────
# Непривилегированный пользователь — тот же, кому принадлежат файлы проекта
User=deploy
Group=deploy
WorkingDirectory=/srv/prokod

# ── Что запускать ──────────────────────────────────────────────────────────
# Полный путь к node обязателен: systemd не читает ваш ~/.bashrc и не знает PATH.
# Проверьте свой путь командой `which node` (NodeSource: /usr/bin/node).
# Запускаем node напрямую, а не через npm: меньше лишних процессов, и сигнал
# остановки приходит сразу приложению, а не обёртке.
ExecStart=/usr/bin/node server/index.js

# ── Переменные окружения ───────────────────────────────────────────────────
# Приложение и само читает .env (server/config.js), но продублировать здесь
# полезно: так значения видны в `systemctl show prokod`, а TZ применится
# и к дочерним процессам. Файл должен быть доступен пользователю deploy.
EnvironmentFile=/srv/prokod/.env
Environment=NODE_ENV=production

# ── Перезапуск после сбоя ──────────────────────────────────────────────────
Restart=always
RestartSec=5
# Если приложение падает чаще 5 раз за минуту — перестать его дёргать
# и остаться в состоянии failed, чтобы это было видно в мониторинге
StartLimitIntervalSec=60
StartLimitBurst=5

# ── Корректная остановка ───────────────────────────────────────────────────
KillSignal=SIGTERM
TimeoutStopSec=20

# ── Журналирование ─────────────────────────────────────────────────────────
# Всё, что приложение печатает, уходит в journald: journalctl -u prokod -f
StandardOutput=journal
StandardError=journal
SyslogIdentifier=prokod

# ── Ограничения безопасности ───────────────────────────────────────────────
# Процесс не может получить новые права (даже через suid-программы)
NoNewPrivileges=true
# Свой изолированный /tmp — процесс не видит чужие временные файлы
PrivateTmp=true
# Вся файловая система только для чтения, кроме явно разрешённого ниже
ProtectSystem=strict
# Чужие домашние каталоги недоступны
ProtectHome=true
# Ядро и его настройки защищены от записи
ProtectKernelTunables=true
ProtectKernelModules=true
ProtectControlGroups=true
# Разрешаем сетевые протоколы только те, что нужны HTTP-серверу
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
RestrictNamespaces=true
LockPersonality=true
# Память нельзя одновременно писать и исполнять — усложняет эксплойты.
# ВНИМАНИЕ: при проблемах со стартом (редко, но бывает с нативными модулями
# и JIT-компилятором) закомментируйте эту строку первой.
MemoryDenyWriteExecute=false

# Единственные места, куда приложению разрешено писать:
#   data/    — база SQLite, журнал WAL, файл-флаг блокировки
#   backups/ — архивы npm run backup
ReadWritePaths=/srv/prokod/data /srv/prokod/backups

[Install]
WantedBy=multi-user.target
```

> ⚠️ **Осторожно:** при `ProtectSystem=strict` пути из `ReadWritePaths` **должны

>
> ```bash
> mkdir -p /srv/prokod/data /srv/prokod/backups
> ```

**Включите и запустите службу:**

sudo systemctl enable prokod          # включить автозапуск при загрузке сервера

<a id="38-альтернатива-pm2"></a>

### 3.8 Альтернатива: PM2

PM2 — популярный менеджер процессов для Node. Он умеет то же, что systemd, плюс удобный
просмотр логов и метрик. Если вы уже привыкли к нему — пользуйтесь, но с одной жёсткой
оговоркой.

```bash
sudo npm install -g pm2
cd /srv/prokod
pm2 start server/index.js --name prokod --time
pm2 save                      # запомнить список процессов
pm2 startup systemd           # напечатает команду — выполните её с sudo
```

Последняя команда выведет строку вида
`sudo env PATH=$PATH:/usr/bin pm2 startup systemd -u deploy --hp /home/deploy` —
скопируйте её и выполните. Это создаст systemd-юнит, который поднимет PM2 при загрузке.
Иными словами, PM2 всё равно работает поверх systemd, просто добавляет свой слой.

Полезные команды:

```bash
pm2 status                 # список процессов
pm2 logs prokod            # логи
pm2 restart prokod         # перезапуск
pm2 monit                  # интерактивный монитор
```

> ⚠️ **Осторожно: никогда не запускайте этот проект в cluster-режиме.**
> Команды **`pm2 start server/index.js -i max`**, **`-i 4`**, **`--instances`** для «ПроКода»
> запрещены. PM2 поднимет несколько процессов на одну базу SQLite и на одни и те же
> счётчики в памяти — со всеми последствиями из [3.7](#37-автозапуск-systemd):
> `database is locked`, разъезжающиеся данные, сломанные ограничители частоты.
> Используйте только режим `fork` (он по умолчанию, когда флаг `-i` не указан).
>
> Проверить: `pm2 describe prokod` — в поле `exec mode` должно быть **`fork_mode`**,
> а `instances` — **1**.

**Что выбрать.** Для одного приложения на сервере **systemd лучше**: он уже есть в системе,
не требует глобального пакета, его перезапуск и журнал единообразны с остальными службами,
и ограничения безопасности (`ProtectSystem`, `ReadWritePaths`) настраиваются декларативно.
PM2 оправдан, когда на сервере живёт несколько Node-приложений и вам нужен общий пульт
управления ими.

**Про Forever.** Инструмент `forever` встречается в старых инструкциях — он давно
не развивается, последний значимый релиз был много лет назад, и он не умеет ни нормально
запускаться при загрузке системы, ни ограничивать права процесса. Не используйте.

Документация: [systemd.io](https://systemd.io/),
[man systemd.service](https://www.freedesktop.org/software/systemd/man/systemd.service.html),
[pm2.keymetrics.io](https://pm2.keymetrics.io/docs/usage/quick-start/).

<a id="39-nginx-как-обратный-прокси"></a>

### 3.9 Nginx как обратный прокси

Node сейчас слушает порт 3000. Нужен веб-сервер, который примет запросы на 80 и 443,
завершит HTTPS и передаст их приложению. Эту роль играет nginx.

Зачем он вообще нужен, если Node умеет отвечать сам:

- **HTTPS-сертификат** — certbot умеет автоматически настраивать nginx и продлевать
  сертификат без остановки сайта;
- **порт 80/443 без прав root** — приложение остаётся под непривилегированным `deploy`;
- **лишняя защита** — nginx отсекает мусорные запросы, обрывает медленные соединения,
  ограничивает размер тела;
- **дополнительный рубеж ограничения частоты** (`limit_req`), не зависящий от памяти
  Node-процесса.

**Установка:**

```bash
sudo apt install -y nginx
```

Проверьте, что nginx поднялся: откройте в браузере `http://YOUR_SERVER_IP` — должна
появиться страница «Welcome to nginx!».

**Создайте конфиг сайта:**

```bash
sudo nano /etc/nginx/sites-available/prokod
```

**Стартовый конфиг (только HTTP — HTTPS добавит certbot автоматически):**

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name prokod.ru www.prokod.ru;

    # Куда nginx пишет журналы этого сайта
    access_log /var/log/nginx/prokod.access.log;
    error_log  /var/log/nginx/prokod.error.log;

    # Максимальный размер тела запроса. Приложение само ограничивает JSON 64 килобайтами
    # (express.json({ limit: '64kb' }) в server/index.js), файлов оно не принимает.
    # 1 мегабайт — комфортный запас, всё лишнее отсекается ещё до Node.
    client_max_body_size 1m;

    # Не сообщать версию nginx в заголовках и на страницах ошибок
    server_tokens off;

    location / {
        # Приложение слушает только локальный адрес
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;

        # ── Заголовки, без которых приложение «ослепнет» ────────────────────
        # Настоящий адрес посетителя. Именно его читает Express при TRUST_PROXY=1,
        # и по нему считаются ограничения частоты и блокировка перебора пароля.
        # ВАЖНО: $remote_addr, а НЕ $proxy_add_x_forwarded_for — см. предупреждение
        # в разделе 3.5. Второй вариант дописывает адрес к заголовку, который прислал
        # клиент, и позволяет подделать IP, обойдя все ограничения.
        proxy_set_header X-Real-IP        $remote_addr;
        proxy_set_header X-Forwarded-For  $remote_addr;
        # http или https — по нему приложение понимает, что соединение защищено
        proxy_set_header X-Forwarded-Proto $scheme;
        # Исходное имя хоста: нужно для проверки заголовка Origin на изменяющих запросах
        proxy_set_header Host             $host;
        proxy_set_header X-Forwarded-Host $host;

        # ── Таймауты ───────────────────────────────────────────────────────
        proxy_connect_timeout 10s;   # сколько ждать соединения с Node
        proxy_send_timeout    60s;   # сколько ждать при отправке запроса
        proxy_read_timeout    60s;   # сколько ждать ответа

        # Не буферизовать ответы: страницы небольшие, отдача идёт быстрее
        proxy_buffering off;

        # ── Двойное сжатие ────────────────────────────────────────────────
        # В приложении включён middleware compression. Если включить gzip
        # и здесь, ответ будет сжат дважды — подробности в разделе 5.2.
        gzip off;
    }
}
```

**Включите сайт и уберите страницу-заглушку nginx:**

```bash
sudo ln -s /etc/nginx/sites-available/prokod /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t
```

- `ln -s` создаёт символическую ссылку — так nginx узнаёт, что сайт включён;
- `rm` убирает дефолтный сайт, иначе он будет перехватывать запросы по IP;
- `nginx -t` проверяет синтаксис.

Ожидаемый ответ `nginx -t`:

```
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
```

Применяем:

```bash
sudo systemctl reload nginx
```

`reload` применяет конфиг **без разрыва** текущих соединений, в отличие от `restart`.

Проверьте: `curl -I http://YOUR_SERVER_IP/` — должно вернуться `HTTP/1.1 200 OK`
и заголовки от приложения (`Content-Security-Policy`, `X-Frame-Options: DENY`).

> ⚠️ **Осторожно: порт 3000 сейчас открыт наружу.** Приложение вызывает
> `app.listen(config.port)` без указания адреса — значит, оно слушает **все сетевые
> интерфейсы**, включая внешний. Прямо сейчас `http://YOUR_SERVER_IP:3000` открывается
> в обход nginx: без HTTPS, без ограничений nginx и с неправильным определением IP клиента.
>
> Отдельной переменной вроде `HOST` в проекте нет. Закрыть это можно двумя способами.
>
> **Способ 1 (рекомендуемый, ничего не меняет в коде): файрвол.** Настройте `ufw`
> из [5.3](#53-файрвол-ufw) — он разрешает только 22, 80 и 443, а 3000 закрывает.
> Проверка снаружи (со своего компьютера):
>
> ```bash
> curl -m 5 http://YOUR_SERVER_IP:3000/
> ```
>
> Должно зависнуть и завершиться таймаутом или `Connection refused` — значит, порт закрыт.
>
> **Способ 2 (правка кода, одна строка).** В `server/index.js` найдите
> `const server = app.listen(config.port, () => {` и добавьте адрес:
>
> ```js
> const server = app.listen(config.port, '127.0.0.1', () => {
> ```
>
> Тогда приложение физически не принимает соединения извне. Минус: это локальное изменение
> в отслеживаемом git-файле — при `git pull` возникнет конфликт, а при `git checkout` правка
> потеряется. Если делаете так, оформите её коммитом в своей ветке, а не «на живую».
>
> Лучше всего — оба способа сразу: файрвол как основной рубеж, привязка к localhost
> как страховка на случай ошибки в правилах файрвола.

Документация nginx: [nginx.org/ru/docs](https://nginx.org/ru/docs/),
[модуль proxy](https://nginx.org/ru/docs/http/ngx_http_proxy_module.html).

<a id="310-https-certbot-и-lets-encrypt"></a>

### 3.10 HTTPS: Certbot и Let's Encrypt

Let's Encrypt выдаёт бесплатные сертификаты сроком на 90 дней, Certbot получает
и продлевает их автоматически.

> ⚠️ **Осторожно:** прежде чем выпускать сертификат, домен **уже должен указывать
> на этот сервер**. Let's Encrypt проверяет владение доменом, обращаясь к нему по HTTP.
> Сначала настройте DNS ([раздел 4](#4-настройка-домена)), дождитесь, пока
> `nslookup prokod.ru` показывает ваш IP, и только потом запускайте certbot.

**Установка (через snap — официально рекомендуемый способ):**

```bash
sudo snap install core && sudo snap refresh core
sudo snap install --classic certbot
sudo ln -s /snap/bin/certbot /usr/bin/certbot
```

Альтернатива, если snap не хочется: `sudo apt install -y certbot python3-certbot-nginx`
(версия из репозитория Ubuntu может быть старее, но для наших задач подходит).

**Выпуск сертификата:**

```bash
sudo certbot --nginx -d prokod.ru -d www.prokod.ru
```

Certbot задаст три вопроса:

1. **Email** — на него придёт письмо, если сертификат вдруг не продлится. Укажите рабочий,
   который вы читаете.
2. **Согласие с условиями** (Terms of Service) — `Y`.
3. **Рассылка EFF** — на ваше усмотрение, `N` ничего не ломает.

Дальше certbot сам:

- проверит владение доменом (положит временный файл, который Let's Encrypt заберёт по HTTP);
- получит сертификат в `/etc/letsencrypt/live/prokod.ru/`;
- **перепишет ваш конфиг nginx**: добавит блок `listen 443 ssl`, пути к сертификату
  и отдельный сервер с редиректом с HTTP на HTTPS;
- перезагрузит nginx.

Успешное завершение выглядит так:

```
Successfully received certificate.
Certificate is saved at: /etc/letsencrypt/live/prokod.ru/fullchain.pem
Key is saved at:         /etc/letsencrypt/live/prokod.ru/privkey.pem
This certificate expires on 2026-11-07.
Deploying certificate
Successfully deployed certificate for prokod.ru to /etc/nginx/sites-enabled/prokod
Congratulations! You have successfully enabled HTTPS on https://prokod.ru
```

Откройте `https://prokod.ru` — должен появиться замок в адресной строке.

**Автопродление и его проверка.** Certbot ставит systemd-таймер, который дважды в сутки
проверяет, не пора ли продлевать (продление происходит за 30 дней до истечения).
Убедитесь, что таймер активен:

```bash
sudo systemctl list-timers | grep certbot
```

Ожидается строка с `snap.certbot.renew.timer` и временем следующего запуска.

**Обязательно прогоните репетицию продления:**

```bash
sudo certbot renew --dry-run
```

Команда выполнит весь процесс продления «понарошку», не тратя лимиты Let's Encrypt.
Ожидаемая концовка:

```
Congratulations, all simulated renewals succeeded:
  /etc/letsencrypt/live/prokod.ru/fullchain.pem (success)
```

Если здесь ошибка — сертификат не продлится и через 90 дней сайт покажет всем страшное
предупреждение браузера. Разберитесь сейчас, а не потом.

> 💡 **Совет:** типичная причина провала автопродления — кто-то потом добавил в nginx
> правило, которое перехватывает `/.well-known/acme-challenge/` (например, «редиректить
> вообще всё на HTTPS» или «отдавать 404 на всё неизвестное»). Проверяйте `--dry-run`
> после каждой существенной правки конфига nginx.

Документация: [certbot.eff.org](https://certbot.eff.org/instructions),
[letsencrypt.org/ru/docs](https://letsencrypt.org/ru/docs/).

<a id="311-альтернатива-caddy"></a>

### 3.11 Альтернатива: Caddy

Caddy — веб-сервер, который **сам получает и продлевает сертификаты Let's Encrypt**,
без certbot и без отдельной настройки. Для новичка это заметно проще nginx: конфиг
из пяти строк вместо пятидесяти, и нечему сломаться при продлении.

**Установка:**

```bash
sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https curl
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' \
  | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' \
  | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt update && sudo apt install -y caddy
```

**Конфигурация целиком:**

```bash
sudo nano /etc/caddy/Caddyfile
```

```caddy
prokod.ru, www.prokod.ru {
	reverse_proxy 127.0.0.1:3000
	encode gzip
	header -Server
}
```

Что здесь происходит:

- `prokod.ru, www.prokod.ru` — для этих доменов Caddy сам выпустит сертификат при первом
  запуске и будет продлевать его автоматически. HTTP автоматически редиректится на HTTPS —
  отдельно настраивать не нужно;
- `reverse_proxy 127.0.0.1:3000` — передаёт запросы приложению. Заголовки
  `X-Forwarded-For`, `X-Forwarded-Proto` и `Host` Caddy проставляет **сам**, по умолчанию —
  значит, `TRUST_PROXY=1` в `.env` работает без дополнительных настроек;
- `encode gzip` — сжатие на прокси. **Если оставляете эту строку, уберите middleware
  `compression` из `server/index.js`** — иначе двойное сжатие, см. [5.2](#52-двойное-сжатие).
  Проще: удалите строку `encode gzip` и оставьте сжатие в приложении;
- `header -Server` — убрать заголовок с именем сервера.

**Запуск:**

```bash
sudo systemctl reload caddy
sudo systemctl status caddy
sudo journalctl -u caddy -f     # здесь видно, как выпускается сертификат
```

> ⚠️ **Осторожно:** nginx и Caddy нельзя запускать одновременно — оба хотят порты 80 и 443.
> Если пробуете Caddy после nginx, сначала `sudo systemctl disable --now nginx`.

**Что выбрать.** Caddy проще и «самоуправляемее». Nginx — стандарт индустрии: под него
больше готовых рецептов, его знают все администраторы, у него тоньше настройки кэша
и ограничений. Для проекта такого размера **оба варианта равноценны** — берите тот,
в котором вам комфортнее разбираться. Дальше в документе (раздел 5) подробные рецепты
даны для nginx.

Документация: [caddyserver.com/docs](https://caddyserver.com/docs/).

<a id="312-обновление-проекта-и-откат"></a>

### 3.12 Обновление проекта и откат

**Ручное обновление, по шагам:**

```bash
cd /srv/prokod
npm run backup                       # 1. страховка: копия данных ДО обновления
git pull                             # 2. забрать свежий код
npm ci --omit=dev                    # 3. обновить зависимости по lock-файлу
sudo systemctl restart prokod        # 4. перезапустить службу
sudo systemctl status prokod         # 5. убедиться, что active (running)
curl -I http://127.0.0.1:3000/       # 6. убедиться, что отвечает 200 OK
```

> ⚠️ **Осторожно:** шаг 4 (перезапуск) обязателен даже тогда, когда поменялась только
> разметка. Хэши инлайновых скриптов для Content-Security-Policy считаются **один раз
> при старте сервера** (`server/csp.js`). Если после `git pull` не перезапустить службу,
> браузер заблокирует микроразметку лендинга: страница откроется, но в консоли будет
> ошибка CSP, а поисковики разметку не увидят. То же касается любых правок
> `public/index.html` прямо на сервере.

**Скрипт деплоя.** Чтобы не выполнять шесть команд вручную и не забыть перезапуск,
положите в проект файл `deploy.sh`:

```bash
nano /srv/prokod/deploy.sh
```

```bash
#!/usr/bin/env bash
# Обновление «ПроКод» на боевом сервере.
# Запуск: ./deploy.sh   (из /srv/prokod, под пользователем deploy)

set -euo pipefail
# -e  прервать при первой ошибке
# -u  ошибка при обращении к незаданной переменной
# -o pipefail  ошибка в конвейере не проглатывается

APP_DIR="/srv/prokod"
SERVICE="prokod"

cd "$APP_DIR"

echo "==> 1/6 Резервная копия данных"
npm run backup

echo "==> 2/6 Текущая версия (запомните её для отката)"
git rev-parse --short HEAD | tee /tmp/prokod-prev-commit

echo "==> 3/6 Загрузка кода"
git pull --ff-only
# --ff-only: обновиться, только если история идёт «в перёд».
# Если на сервере кто-то правил файлы, команда честно откажется, а не создаст мердж.

echo "==> 4/6 Зависимости"
npm ci --omit=dev

echo "==> 5/6 Перезапуск службы"
sudo systemctl restart "$SERVICE"
sleep 3

echo "==> 6/6 Проверка"
systemctl is-active --quiet "$SERVICE" || { echo "СЛУЖБА НЕ ЗАПУСТИЛАСЬ"; exit 1; }

code=$(curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:3000/)
if [ "$code" != "200" ]; then
  echo "Сайт отвечает $code вместо 200 — смотрите journalctl -u $SERVICE -n 50"
  exit 1
fi

echo
echo "Готово. Версия: $(git rev-parse --short HEAD)"
echo "Журнал: sudo journalctl -u $SERVICE -f"
```

Сделайте файл исполняемым и разрешите пользователю `deploy` перезапускать службу
без ввода пароля (иначе скрипт остановится на запросе пароля):

```bash
chmod +x /srv/prokod/deploy.sh
sudo visudo -f /etc/sudoers.d/prokod-deploy
```

В открывшемся редакторе одна строка:

```

```

Это даёт право только на четыре конкретные команды с конкретной службой, а не полный
`sudo` без пароля.

Теперь обновление — одна команда:

```bash
cd /srv/prokod && ./deploy.sh
```

**Откат.** Если после обновления что-то сломалось:

```bash

git log --oneline -5                 # посмотреть последние версии

<a id="42-dns-записи"></a>

### 4.2 DNS-записи

DNS — телефонная книга интернета: она переводит `prokod.ru` в IP-адрес `YOUR_SERVER_IP`.
Записи настраиваются в панели регистратора (раздел «DNS-серверы и управление зоной»,
«DNS-записи» или похожий).

**Минимальный набор для проекта:**

| Тип | Имя (Host) | Значение | TTL | Зачем |
|---|---|---|---|---|
| `A` | `@` | `YOUR_SERVER_IP` | 3600 | Основной домен `prokod.ru` → ваш сервер |
| `A` | `www` | `YOUR_SERVER_IP` | 3600 | `www.prokod.ru` → тот же сервер |

Пояснения к полям:

- **`@`** означает сам домен без поддомена (`prokod.ru`). В некоторых панелях вместо `@`
  пишут пустое значение или полное имя `prokod.ru.` — с точкой на конце.
- **`www`** — поддомен. Вместо второй `A`-записи можно сделать
  `CNAME www → prokod.ru.` (псевдоним). Разница: с `CNAME` при смене сервера меняется одна
  запись вместо двух. С двумя `A`-записями чуть быстрее резолвится. Для нашего случая
  разницы никакой — берите то, что понятнее.
- **`TTL`** (time to live) — сколько секунд провайдеры и браузеры держат ответ в кэше.
  `3600` = час. Это и есть ответ на вопрос «почему изменения не видны сразу»: пока
  не истечёт TTL старой записи, часть интернета продолжает видеть прежний адрес.

> 💡 **Совет:** если планируете переезд, **за сутки до него** снизьте TTL до 300 секунд.
> Тогда переключение на новый IP разойдётся по интернету за 5 минут, а не за час.
> После переезда верните 3600 — это снижает нагрузку и ускоряет отклик.

**Сколько ждать.** Обычно 15 минут – 2 часа. При смене самих NS-серверов (не записей,
а серверов имён) — до 24 часов, изредка до 72. Это нормально и от вас не зависит.

**Записи, которые понадобятся позже** (не сейчас, а когда будете подключать почту, —
см. [6.2](#62-почта-на-домене)):

| Тип | Имя | Значение | Зачем |
|---|---|---|---|
| `MX` | `@` | сервер почтового провайдера | куда доставлять письма на `@prokod.ru` |
| `TXT` | `@` | `v=spf1 ...` | SPF: кому разрешено слать письма от вашего имени |
| `TXT` | `mail._domainkey` | `v=DKIM1; ...` | DKIM: подпись писем |
| `TXT` | `_dmarc` | `v=DMARC1; p=none; ...` | DMARC: что делать с письмами, не прошедшими проверку |

<a id="43-проверка-dns"></a>

### 4.3 Проверка DNS

**Windows (PowerShell или cmd):**

```powershell
nslookup prokod.ru
nslookup www.prokod.ru
```

Ожидаемый вывод:

```
Server:  UnKnown
Address:  192.168.1.1

Не заслуживающий доверия ответ:
Имя:     prokod.ru
Address: 203.0.113.25
```

Строка «Не заслуживающий доверия ответ» (`Non-authoritative answer`) — это норма,
она означает лишь «ответ из кэша ближайшего DNS-сервера». Важно, что `Address`
совпадает с вашим `YOUR_SERVER_IP`.

**Linux / macOS:**

```bash
dig +short prokod.ru A          # только IP, коротко
dig prokod.ru A                 # подробно, с TTL и секцией ANSWER
dig +short www.prokod.ru A
dig prokod.ru NS                # какие серверы имён обслуживают домен
```

**Проверить, что видит весь мир, а не только ваш провайдер:**

```bash
# спросить напрямую у публичных резолверов, минуя кэш провайдера
dig @8.8.8.8 +short prokod.ru
dig @77.88.8.8 +short prokod.ru      # DNS Яндекса
```

Или через веб-сервисы: [dnschecker.org](https://dnschecker.org/),
[whatsmydns.net](https://www.whatsmydns.net/) — они показывают ответ из десятков стран сразу.

**Проверить, что сервер отвечает именно на это имя:**

```bash
curl -I http://prokod.ru/
```

Ожидается `HTTP/1.1 301 Moved Permanently` с `Location: https://prokod.ru/` — после
настройки HTTPS, или `200 OK` — если сертификата ещё нет.

<a id="44-cloudflare-честный-разбор"></a>

### 4.4 Cloudflare: честный разбор

Cloudflare — популярный сервис, который ставится «перед» вашим сайтом: кэширует статику,
скрывает реальный IP, защищает от DDoS, выдаёт бесплатный сертификат. В большинстве
англоязычных инструкций его советуют по умолчанию.

> ⚠️ **Осторожно: для сайта, рассчитанного на российских родителей, Cloudflare в 2026 году
> скорее навредит.**
>
> Роскомнадзор системно ограничивает работу Cloudflare на территории России:
>
> - **с ноября 2024 года** блокируется технология ECH (Encrypted Client Hello),
>   которую Cloudflare включил по умолчанию, — из-за этого сайты за Cloudflare
>   у части российских провайдеров перестали открываться вовсе;
> - **с июня 2025 года** фиксируется замедление и обрыв соединений с ресурсами
>   Cloudflare: соединение обрывается примерно после первых 16 КБ переданных данных.
>   Практически это выглядит так: страница начинает грузиться, показывается «половина»
>   сайта, стили и скрипты не догружаются, форма заявки не отправляется.
>
> Ограничения применяются неравномерно — у разных операторов и в разных регионах картина
> отличается, — что делает диагностику мучительной: у вас всё открывается, а половина
> родителей пишет «сайт не работает». Для лендинга, который должен продавать занятия,
> это неприемлемо.

**Что делать вместо Cloudflare для `prokod.ru`:**

1. **Ничего.** Для проекта такого масштаба достаточно nginx + Let's Encrypt на своём
   сервере. Трафик небольшой, статика лёгкая, кэширование настроено самим приложением
   (`Cache-Control` с ревалидацией по ETag). CDN здесь решает несуществующую проблему.
2. **Российский CDN и защита от DDoS**, если она действительно понадобится:
   - [Selectel CDN](https://selectel.ru/services/additional/cdn/)
   - [Yandex Cloud CDN](https://yandex.cloud/ru/services/cdn)
   - [DDoS-Guard](https://ddos-guard.net/) — фильтрация трафика и CDN, российская компания
   - [StormWall](https://stormwall.pro/) — то же, с центрами очистки в РФ
   - многие хостеры (Timeweb, Selectel, Aeza) предлагают базовую защиту от DDoS
     как опцию к тарифу.
3. **Защита от «шумных» ботов** уже частично встроена: ограничители частоты в приложении
   и `limit_req` в nginx ([5.1](#51-боевой-конфиг-nginx)) отсекают примитивный перебор.

**Если аудитория за рубежом и Cloudflare всё-таки нужен.** Порядок подключения:

1. Зарегистрируйтесь на [cloudflare.com](https://dash.cloudflare.com/sign-up), добавьте
   домен `prokod.ru`, выберите бесплатный план.
2. Cloudflare просканирует существующие DNS-записи. Проверьте, что `A @` и `A www`
   указывают на ваш `YOUR_SERVER_IP`.
3. Cloudflare выдаст два своих NS-сервера (вида `xxx.ns.cloudflare.com`). Пропишите их
   в панели регистратора вместо текущих. Ждать до 24 часов.
4. **SSL/TLS → Overview → выберите режим `Full (strict)`.**
5. SSL/TLS → Edge Certificates → включите `Always Use HTTPS`.
6. Speed → Optimization: **отключите** Rocket Loader и минификацию JS/CSS. Rocket Loader
   меняет способ загрузки скриптов и конфликтует с Content-Security-Policy без
   `unsafe-inline` — а в этом проекте CSP именно такая (`server/csp.js`).

> ⚠️ **Осторожно с режимом SSL.** Cloudflare предлагает четыре режима, и по умолчанию
> часто оказывается `Flexible`. Это ловушка:
>
> | Режим | Браузер → Cloudflare | Cloudflare → ваш сервер | Итог |
> |---|---|---|---|
> | `Off` | HTTP | HTTP | без шифрования |
> | **`Flexible`** | HTTPS | **HTTP** | «полу-HTTPS»: замок в браузере есть, но половина пути открыта. Плюс приложение видит `X-Forwarded-Proto: http` |
> | `Full` | HTTPS | HTTPS, сертификат не проверяется | лучше, но подмена возможна |
> | **`Full (strict)`** | HTTPS | HTTPS с проверкой сертификата | **правильный вариант** |
>
> При `Flexible` в связке с редиректом «HTTP → HTTPS» на вашем nginx вы получите
> бесконечный цикл переадресаций (`ERR_TOO_MANY_REDIRECTS`) — самая частая жалоба
> новичков на Cloudflare.

7. Если Cloudflare включён, реальный IP посетителя приезжает в заголовке `CF-Connecting-IP`,
   а `X-Forwarded-For` содержит цепочку. Приложение читает стандартный `X-Forwarded-For`
   (Express + `TRUST_PROXY=1`), поэтому в nginx стоит подставлять настоящий адрес через
   модуль `ngx_http_realip_module` со списком сетей Cloudflare
   ([cloudflare.com/ips](https://www.cloudflare.com/ips/)). Иначе все посетители снова
   станут «одним IP» — с последствиями из [3.5](#35-файл-env-для-продакшена).

Документация: [developers.cloudflare.com/ssl](https://developers.cloudflare.com/ssl/).

<a id="45-проверка-https-и-www"></a>

### 4.5 Проверка https и www

После выпуска сертификата проверьте все четыре варианта адреса. Правильное поведение:
любой из них приводит на `https://prokod.ru/`.

```bash
curl -sI http://prokod.ru/       | head -n 3
curl -sI http://www.prokod.ru/   | head -n 3
curl -sI https://www.prokod.ru/  | head -n 3
curl -sI https://prokod.ru/      | head -n 3
```

Ожидается:

| Запрос | Ответ | Заголовок Location |
|---|---|---|
| `http://prokod.ru/` | `301` | `https://prokod.ru/` |
| `http://www.prokod.ru/` | `301` | `https://www.prokod.ru/` или сразу `https://prokod.ru/` |
| `https://www.prokod.ru/` | `301` | `https://prokod.ru/` |
| `https://prokod.ru/` | `200 OK` | — |

Certbot по умолчанию делает редирект только с HTTP на HTTPS, но **не** склеивает `www`
и основной домен. Чтобы `www` уходил на основной, добавьте в конфиг nginx отдельный блок:

```nginx
# Отдельный сервер только для www: принимает и сразу отправляет на основной домен
server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name www.prokod.ru;

    # Тот же сертификат: он выпущен сразу на оба имени (-d prokod.ru -d www.prokod.ru)
    ssl_certificate     /etc/letsencrypt/live/prokod.ru/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/prokod.ru/privkey.pem;
    include /etc/letsencrypt/options-ssl-nginx.conf;
    ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem;

    # 301 — постоянный редирект: поисковики перенесут вес страницы на основной адрес
    return 301 https://prokod.ru$request_uri;
}
```

И уберите `www.prokod.ru` из `server_name` основного блока — иначе два блока будут
спорить за одно имя, и nginx предупредит про `conflicting server name`.

Применить: `sudo nginx -t && sudo systemctl reload nginx`.

**Дополнительные проверки:**

- **Качество TLS:** [ssllabs.com/ssltest](https://www.ssllabs.com/ssltest/) — введите
  домен, через пару минут получите оценку. С конфигом из [5.1](#51-боевой-конфиг-nginx)
  ожидается A или A+.
- **Смешанный контент:** откройте сайт, нажмите F12 → Console. Не должно быть предупреждений
  `Mixed Content`. В этом проекте все ссылки на ресурсы относительные, так что проблемы
  быть не должно — но проверить стоит.
- **Мобильные:** откройте сайт с телефона по реальному 4G, а не по домашнему Wi-Fi.

```

> ⚠️ **Осторожно:** после правки `public/index.html` **обязательно перезапустите службу**
> (`sudo systemctl restart prokod`). Хэши инлайновых блоков `<script type="application/ld+json">`
> для Content-Security-Policy считаются при старте сервера. Изменили микроразметку и не
> перезапустили — браузер её заблокирует, а поисковик не увидит. См. `server/csp.js`.
>
> И правьте эти файлы **в репозитории**, а не прямо на сервере: иначе следующий `git pull`
> либо затрёт правки, либо упрётся в конфликт.

Заодно проверьте остальные пункты списка «Что заменить перед публикацией» в
[README.md](README.md): отзывы, цифры на первом экране, цены направлений, юридическую
строку в футере, страницы `privacy.html` и `oferta.html`.

## 5. Оптимизация и безопасность

<a id="51-боевой-конфиг-nginx"></a>

### 5.1 Боевой конфиг nginx

Ниже — полный рабочий конфиг с комментариями. Он заменяет тот, что был в
[3.9](#39-nginx-как-обратный-прокси), и включает всё, что нужно боевому сайту.
Если сертификат уже выпущен certbot, часть строк у вас уже есть — сверьтесь и допишите
недостающее.

**Сначала общие настройки** (файл `/etc/nginx/nginx.conf`, блок `http`) — там нужны
две строки для ограничителя частоты:

```bash
sudo nano /etc/nginx/nginx.conf
```

Внутри `http { ... }` добавьте:

```nginx
    # Не показывать версию nginx в заголовке Server и на страницах ошибок
    server_tokens off;

    # Зоны ограничения частоты. Память общая на все сайты, поэтому объявляются здесь.
    # 10m хватает примерно на 160 тысяч уникальных адресов.
    # $binary_remote_addr — IP клиента в компактном виде.
    limit_req_zone $binary_remote_addr zone=prokod_general:10m rate=20r/s;
    limit_req_zone $binary_remote_addr zone=prokod_login:10m   rate=10r/m;
    limit_req_zone $binary_remote_addr zone=prokod_form:10m    rate=20r/m;
```

**Теперь сам сайт** — `/etc/nginx/sites-available/prokod`:

```nginx
# ─────────────────────────────────────────────────────────────────────────────
# HTTP: только редирект на HTTPS. Ничего другого здесь не отдаётся.
# ─────────────────────────────────────────────────────────────────────────────
server {
    listen 80;
    listen [::]:80;
    server_name prokod.ru www.prokod.ru;

    # Исключение: путь проверки Let's Encrypt должен отвечать по HTTP,
    # иначе certbot не сможет продлить сертификат.
    location /.well-known/acme-challenge/ {
        root /var/www/html;
    }

    location / {
        return 301 https://prokod.ru$request_uri;
    }
}

# ─────────────────────────────────────────────────────────────────────────────
# HTTPS для www: сразу отправляем на основной домен
# ─────────────────────────────────────────────────────────────────────────────
server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name www.prokod.ru;

    ssl_certificate     /etc/letsencrypt/live/prokod.ru/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/prokod.ru/privkey.pem;
    include /etc/letsencrypt/options-ssl-nginx.conf;
    ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem;

    return 301 https://prokod.ru$request_uri;
}

# ─────────────────────────────────────────────────────────────────────────────
# Основной сайт
# ─────────────────────────────────────────────────────────────────────────────
server {
    # HTTP/2 включаем параметром listen — эта запись работает во ВСЕХ версиях nginx,
    # включая 1.24 из штатного репозитория Ubuntu 24.04. Отдельная директива
    # «http2 on;» появилась только в nginx 1.25.1: на 1.24 она валит конфиг
    # с ошибкой «unknown directive "http2"». Подробнее — в блоке под конфигом.
    listen 443 ssl http2;
    listen [::]:443 ssl http2;

    server_name prokod.ru;

    # ── Сертификаты ─────────────────────────────────────────────────────────
    ssl_certificate     /etc/letsencrypt/live/prokod.ru/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/prokod.ru/privkey.pem;

    # ── TLS ─────────────────────────────────────────────────────────────────
    # Только современные протоколы. TLS 1.0/1.1 давно небезопасны и не нужны:
    # их не поддерживают только браузеры старше 2015 года.
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_prefer_server_ciphers off;   # для TLS 1.3 выбор шифра лучше оставить клиенту
    ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;

    # Кэш TLS-сессий: повторные подключения не проходят полный хендшейк заново
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 1d;
    ssl_session_tickets off;

    # OCSP stapling: сервер сам приносит подтверждение, что сертификат не отозван —
    # браузеру не нужно ходить к удостоверяющему центру, страница открывается быстрее
    ssl_stapling on;
    ssl_stapling_verify on;
    resolver 77.88.8.8 8.8.8.8 valid=300s;
    resolver_timeout 5s;

    # ── HSTS ────────────────────────────────────────────────────────────────
    # Говорит браузеру: «этот сайт всегда только по HTTPS, полгода даже не пробуй HTTP».
    #
    # ⚠ ВНИМАНИЕ: заголовок необратим на время max-age. Если через месяц HTTPS
    # у вас сломается (не продлился сертификат), браузеры пользователей ОТКАЖУТСЯ
    # открывать сайт по HTTP — и обойти это пользователь не сможет.
    # Включайте, только когда HTTPS уже работает стабильно и certbot renew --dry-run
    # проходит успешно. Начните с max-age=300 (5 минут), убедитесь, что всё хорошо,
    # и только потом ставьте 15768000 (полгода).
    #
    # preload и includeSubDomains не добавлены намеренно: preload означает попадание
    # в список, вшитый в браузеры, откуда выписаться очень долго.
    add_header Strict-Transport-Security "max-age=15768000" always;

    # ── Заголовки безопасности ──────────────────────────────────────────────
    # Приложение выставляет свои: Content-Security-Policy, X-Frame-Options,
    # X-Content-Type-Options, Referrer-Policy (см. server/index.js и server/csp.js).
    # Здесь их НЕ дублируем: CSP из nginx перезаписала бы динамический nonce
    # и сломала платформу. Добавляем только то, чего в приложении нет.
    add_header X-XSS-Protection "0" always;   # устаревший фильтр браузера, лучше выключить явно
    server_tokens off;

    # ── Ограничения запроса ─────────────────────────────────────────────────
    # Приложение принимает JSON не больше 64 КБ и не принимает файлов вовсе.
    client_max_body_size 1m;
    client_body_timeout 15s;
    client_header_timeout 15s;
    # Обрывать соединения, из которых данные идут медленнее 10 байт/с
    send_timeout 30s;

    # ── Сжатие ──────────────────────────────────────────────────────────────
    # ВЫБЕРИТЕ ОДИН СЛОЙ — здесь или в приложении. Подробно в разделе 5.2.
    # Вариант по умолчанию: сжимает приложение, nginx не трогает.
    gzip off;

    access_log /var/log/nginx/prokod.access.log;
    error_log  /var/log/nginx/prokod.error.log warn;

    # ── Общие настройки проксирования ───────────────────────────────────────
    location / {
        # Второй рубеж ограничения частоты. Первый — в самом приложении
        # (см. раздел 5.5). Здесь отсекается грубый флуд, до Node он не доходит.
        # burst=40 — разрешить всплеск до 40 запросов, nodelay — не растягивать их
        # во времени, а пропустить сразу (страница тянет ~15 файлов за раз).
        limit_req zone=prokod_general burst=40 nodelay;

        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        # $remote_addr, а не $proxy_add_x_forwarded_for — иначе клиент подделает IP
        proxy_set_header X-Forwarded-For   $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Host  $host;
        proxy_set_header X-Forwarded-Port  $server_port;

        proxy_connect_timeout 10s;
        proxy_send_timeout    60s;
        proxy_read_timeout    60s;

        proxy_buffering off;
        gzip off;
    }

    # ── Страница входа: жёсткий лимит ───────────────────────────────────────
    # Приложение блокирует 8 неудачных попыток за 15 минут с одного IP,
    # но эти счётчики живут в памяти и обнуляются при перезапуске.
    # Здесь — независимый рубеж: не больше 10 запросов в минуту.
    location = /login {
        limit_req zone=prokod_login burst=5 nodelay;

        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        gzip off;
    }

    # ── Приём заявок с лендинга ─────────────────────────────────────────────
    # Приложение разрешает 5 успешных заявок и 30 любых обращений за 10 минут с IP.
    location = /api/applications {
        limit_req zone=prokod_form burst=10 nodelay;

        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        gzip off;
    }

    # ── Картинки, шрифты, иконки ────────────────────────────────────────────
    # Приложение отдаёт их с Cache-Control: max-age=3600 (час).
    # Шрифты и og-обложка не меняются годами — им можно и больше.
    # CSS и JS сюда НЕ включены намеренно: приложение помечает их no-cache
    # с ревалидацией по ETag, чтобы после деплоя не всплыл старый styles.css
    # поверх новой разметки (см. «Известные ограничения» в README).
    location ~* \.(?:woff2|woff|ttf|otf|eot|ico|png|jpe?g|gif|webp|avif|svg)$ {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;

        # Кэш у клиента на 30 дней. expires перезаписывает заголовок от приложения.
        expires 30d;
        add_header Cache-Control "public, max-age=2592000, immutable";
        access_log off;   # не засорять журнал обращениями за иконками
        gzip off;
    }

    # ── Мелочи ──────────────────────────────────────────────────────────────
    # Не отдавать скрытые файлы, если они каким-то образом окажутся в public/
    location ~ /\.(?!well-known) {
        deny all;
        access_log off;
        log_not_found off;
    }

    # Что показать, если приложение лежит (502/503/504)
    error_page 502 503 504 /nginx-maintenance.html;
    location = /nginx-maintenance.html {
        root /var/www/html;
        internal;
    }
}
```

> отдельную директиву `http2 on;`. Она появилась только в **nginx 1.25.1** (май 2023),
> а в штатном репозитории Ubuntu 24.04 LTS лежит **nginx 1.24** — там она уронит
> конфиг с ошибкой `unknown directive "http2"`, и сайт по HTTPS просто не поднимется.
>
> Проверить свою версию: `nginx -v`. Запись `listen 443 ssl http2;` работает во всех
> версиях: в новых она помечена как устаревшая, но продолжает действовать, и это
> предупреждение в логе безобиднее, чем неработающий сервер. Если у вас 1.25.1
> или новее и хочется убрать предупреждение — уберите `http2` из строк `listen`
> и добавьте отдельной строкой `http2 on;`.

Проверьте, что ограничитель работает и не мешает обычным людям: откройте сайт, походите
по страницам платформы. Если в `/var/log/nginx/prokod.error.log` появляются строки
`limiting requests, excess:` для вашего собственного IP при обычной работе — увеличьте
`burst` или `rate`.

<a id="52-двойное-сжатие"></a>

### 5.2 Двойное сжатие

В `server/index.js` подключён middleware `compression()` — приложение само сжимает ответы
gzip. Это сделано осознанно: без него `styles.css` уезжает клиенту на 65 КБ, а HTML
главной — на 110 КБ.

> ⚠️ **Осторожно:** если на nginx включить `gzip on`, ответ будет **сжат дважды**.
> Node пожмёт тело и поставит `Content-Encoding: gzip`, nginx получит уже сжатый поток
> и — в зависимости от версии и настроек — либо не тронет его (тогда `gzip on` просто
> бесполезен и тратит проверку на каждом ответе), либо, при включённом `gzip_proxied`
> и агрессивных настройках, начнёт распаковывать и паковать заново. Результат:
> процессорное время расходуется зря, ответ не становится меньше, а при неудачном
> стечении настроек браузер получает битый контент.

**Выберите ровно один слой.**

**Вариант А (по умолчанию, ничего менять не нужно): сжимает приложение.**

В конфиге nginx оставьте `gzip off;` — как в примерах выше. Плюс: не трогаем код,
всё работает из коробки. Минус: nginx не умеет отдавать brotli, но и Node тоже —
разницы нет.

**Вариант Б: сжимает nginx.**

Даёт чуть больше контроля (можно настроить уровни, типы, добавить brotli через
динамический модуль) и снимает работу с процесса Node.

Шаг 1 — включить сжатие в nginx (в `http`-блоке `/etc/nginx/nginx.conf` или в блоке
`server`):

```nginx
    gzip on;
    gzip_vary on;                    # добавить заголовок Vary: Accept-Encoding
    gzip_proxied any;                # сжимать и проксированные ответы
    gzip_comp_level 5;               # 1..9; выше 6 почти не даёт выигрыша, но ест CPU
    gzip_min_length 1024;            # мелочь сжимать бессмысленно
    gzip_types
        text/plain
        text/css
        text/xml
        application/json
        application/javascript
        application/xml+rss
        image/svg+xml
        text/csv;
```

Обратите внимание на `text/csv` — иначе выгрузка заявок из платформы поедет несжатой,
а она может быть большой.

Шаг 2 — убрать сжатие из приложения. В `server/index.js` закомментируйте строку:

```js
// app.use(compression());
```

И уберите `gzip off;` из блоков `location` в конфиге nginx.

> ⚠️ **Осторожно:** это правка отслеживаемого git-файла. Сделайте её коммитом
> в репозитории, а не прямо на сервере, иначе `git pull` будет ругаться на конфликт.
> Зависимость `compression` при этом можно оставить в `package.json` — она весит копейки,
> а при возврате к варианту А ничего доустанавливать не придётся.

**Как проверить, что сжатие работает и не дублируется:**

```bash
curl -sI -H "Accept-Encoding: gzip" https://prokod.ru/css/styles.css | grep -i "content-encoding\|content-length"
```

Ожидается **ровно один** заголовок `content-encoding: gzip`. Двух быть не должно.
Сравните размер:

```bash
curl -s -o /dev/null -w "без сжатия: %{size_download} байт\n" https://prokod.ru/css/styles.css
curl -s -o /dev/null -w "со сжатием: %{size_download} байт\n" -H "Accept-Encoding: gzip" https://prokod.ru/css/styles.css
```

Второе число должно быть в 4–6 раз меньше первого.

<a id="53-файрвол-ufw"></a>

### 5.3 Файрвол ufw

`ufw` (Uncomplicated Firewall) — простая надстройка над iptables. Задача: пустить снаружи
только SSH, HTTP и HTTPS, а всё остальное — включая порт 3000 приложения — закрыть.

> ⚠️ **Осторожно: сначала разрешите SSH, потом включайте файрвол.** Если сделать наоборот,
> вы отрежете себе доступ к серверу, и спасёт только KVM-консоль в панели провайдера.

```bash
# 1. Политика по умолчанию: входящее запрещено, исходящее разрешено
sudo ufw default deny incoming
sudo ufw default allow outgoing

# 2. САМОЕ ГЛАВНОЕ — разрешить SSH ДО включения файрвола
sudo ufw allow OpenSSH

# 3. Веб
sudo ufw allow 80/tcp    comment 'HTTP'
sudo ufw allow 443/tcp   comment 'HTTPS'

# 4. Только теперь включаем
sudo ufw enable
```

При `enable` появится вопрос:

```
Command may disrupt existing ssh connections. Proceed with operation (y|n)?
```

Отвечайте `y` — SSH вы уже разрешили пунктом 2.

**Проверка:**

```bash
sudo ufw status verbose
```

Ожидаемый вывод:

```
Status: active
Logging: on (low)
Default: deny (incoming), allow (outgoing), disabled (routed)

To                         Action      From
--                         ------      ----
22/tcp (OpenSSH)           ALLOW IN    Anywhere
80/tcp                     ALLOW IN    Anywhere                   # HTTP
443/tcp                    ALLOW IN    Anywhere                   # HTTPS
22/tcp (OpenSSH (v6))      ALLOW IN    Anywhere (v6)
80/tcp (v6)                ALLOW IN    Anywhere (v6)              # HTTP
443/tcp (v6)               ALLOW IN    Anywhere (v6)              # HTTPS
```

Порта 3000 в списке быть **не должно** — значит, приложение недоступно снаружи напрямую.

**Проверьте это со своего компьютера** (не с сервера!):

```bash
curl -m 5 http://YOUR_SERVER_IP:3000/
```

Ожидается зависание с таймаутом или `Connection refused` — порт закрыт, всё правильно.
Если открылась страница сайта — файрвол не работает, разбирайтесь немедленно:
через порт 3000 сайт доступен без HTTPS и с неправильным определением IP посетителя.

**Полезные команды:**

```bash
sudo ufw status numbered      # правила с номерами
sudo ufw delete 3             # удалить правило номер 3
sudo ufw disable              # выключить файрвол (например, при отладке)
sudo ufw logging on           # включить журнал
```

> 💡 **Совет:** если у вас статический домашний IP, можно ограничить SSH только им:
> `sudo ufw delete allow OpenSSH` и затем `sudo ufw allow from 203.0.113.10 to any port 22`.
> Но убедитесь, что IP действительно статический, — иначе однажды вас не пустят.

Документация: [help.ubuntu.com/community/UFW](https://help.ubuntu.com/community/UFW).

<a id="54-fail2ban-для-nginx"></a>

### 5.4 fail2ban для nginx

SSH мы защитили в [2.9](#29-fail2ban). Теперь добавим правила для веб-сервера — они
блокируют тех, кто перебирает пароли или сканирует сайт в поисках уязвимостей.

```bash
sudo nano /etc/fail2ban/jail.local
```

Допишите в конец файла:

```ini
# Слишком много ошибок аутентификации (нужен, если появится HTTP Basic Auth)
[nginx-http-auth]
enabled  = true
port     = http,https
logpath  = /var/log/nginx/*error.log

# Срабатывание ограничителя limit_req — значит, кто-то долбит сайт
[nginx-limit-req]
enabled  = true
port     = http,https
logpath  = /var/log/nginx/prokod.error.log
findtime = 5m
maxretry = 20
bantime  = 2h

# Боты, которые перебирают /wp-admin, /.env, /phpmyadmin и прочее,
# чего у нас нет: каждый такой запрос даёт 404
[nginx-botsearch]
enabled  = true
port     = http,https
logpath  = /var/log/nginx/prokod.access.log
findtime = 10m
maxretry = 15
bantime  = 6h
```

Своё правило для перебора пароля на странице входа платформы. Приложение отвечает `401`
на неверный логин или пароль — по этому и ловим:

```bash
sudo nano /etc/fail2ban/filter.d/prokod-login.conf
```

```ini
[Definition]
# Ловим POST /login с кодом ответа 401 в журнале доступа nginx.
# <HOST> — стандартный плейсхолдер fail2ban для IP-адреса.
failregex = ^<HOST> .* "POST /login HTTP/[0-9.]+" 401
ignoreregex =
```

И подключаем его в `jail.local`:

```ini
[prokod-login]
enabled  = true
port     = http,https
filter   = prokod-login
logpath  = /var/log/nginx/prokod.access.log
findtime = 15m
maxretry = 10
bantime  = 1h
```

Применить и проверить:

```bash
sudo systemctl restart fail2ban
sudo fail2ban-client status                 # список активных правил
sudo fail2ban-client status prokod-login    # статистика по нашему правилу
```

Проверить, что регулярное выражение вообще что-то ловит:

```bash
sudo fail2ban-regex /var/log/nginx/prokod.access.log /etc/fail2ban/filter.d/prokod-login.conf
```

В выводе смотрите строку `Lines: ... matched`. Если совпадений ноль, а неудачные входы
были — проверьте формат журнала (по умолчанию `combined`, IP идёт первым полем).

**Разбанить себя, если случайно попались:**

```bash
sudo fail2ban-client set prokod-login unbanip 203.0.113.10
```

<a id="55-что-уже-защищено-в-приложении"></a>

### 5.5 Что уже защищено в приложении

Прежде чем накручивать защиту на nginx, посмотрите, что уже сделано в коде. Дублировать
одно и то же на двух уровнях — не «двойная защита», а двойная вероятность что-нибудь
сломать. Полный перечень — в разделе «Технические решения» [README.md](README.md);
здесь краткий список с выводами для настройки сервера.

| Что | Где | Вывод для nginx |
|---|---|---|
| **Content-Security-Policy без `unsafe-inline`** | `server/csp.js` | **Не добавляйте `add_header Content-Security-Policy` в nginx.** Политика содержит одноразовый `nonce`, который меняется на каждом запросе. Статический заголовок из nginx перезапишет динамический и сломает платформу |
| `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy` | `server/index.js` | уже есть, дублировать не нужно |
| **Ограничитель входа**: 8 неудачных попыток за 15 минут с IP | `server/auth.js` | `limit_req` на `/login` — независимый второй рубеж, полезен: счётчики приложения живут в памяти и обнуляются при рестарте |
| **Ограничитель формы**: 5 успешных заявок и 30 любых обращений за 10 минут с IP | `server/routes/public.js` | то же — `limit_req` на `/api/applications` |
| **Ограничитель API платформы**: 300 запросов и не более 90 изменяющих за 5 минут на сотрудника | `server/auth.js` | отдельный лимит на nginx не нужен, хватит общего |
| **Cookie сессии**: подписанная, `HttpOnly`, `SameSite=Lax`, срок 12 часов | `server/auth.js` | ничего не требуется |
| **Проверка заголовка `Origin`** на изменяющих запросах | `server/auth.js` | обязательно передавайте `proxy_set_header Host $host;` — иначе приложение решит, что запрос пришёл с чужого домена, и вернёт ошибку |
| **Пароли**: scrypt с солью, проверка ~50 мс, сравнение за постоянное время | `server/auth.js` | — |
| **Экранирование формул при выгрузке в CSV** | `server/routes/api/applications.js` | защита от «CSV injection» в Excel |
| **Данные в интерфейс только через `textContent`** | `public/js/crm/*` | XSS через заявку или комментарий невозможен |
| **Кэш `/app`**: `no-store, private` | `server/index.js` | **не добавляйте кэширование `/app` на nginx** — там персональные данные |
| **Лимит тела JSON — 64 КБ** | `server/index.js` | `client_max_body_size 1m` в nginx — грубый фильтр перед ним |

**Про доступность порта наружу** — приложение слушает все интерфейсы, это закрывается
файрволом, см. [3.9](#39-nginx-как-обратный-прокси) и [5.3](#53-файрвол-ufw).

<a id="56-секреты-и-пароли"></a>

### 5.6 Секреты и пароли

**1. Смените `ADMIN_PASSWORD`.** В `.env.example` лежит `procode2025`. Если оставить его,
сервер при каждом старте печатает предупреждение:

```
  ⚠  ВНИМАНИЕ
     • ADMIN_PASSWORD остался стандартным («procode2025»). Перед публикацией сайта
       задайте свой пароль в файле .env.
```

Этот вход работает, **только пока не заведён ни один сотрудник**. Но он ваш запасной
ключ на случай, если файл учётных записей будет потерян, — сделайте его нормальным.

**2. Чем плохи стандартные пароли.** Боты сканируют интернет и пробуют пары вида
`admin/admin`, `admin/password`, а также пароли, «характерные для CMS» — а `procode2025`
попадёт в их списки, как только проект где-нибудь опубликуют. Кроме того, у вас в базе
персональные данные детей: утечка — это не только неприятность, но и ответственность
по 152-ФЗ.

Требования к нормальному паролю администратора:

- длина от 16 символов (длина важнее «сложности»);
- не встречается в других ваших сервисах;
- хранится в менеджере паролей (Bitwarden, KeePassXC, 1Password), а не в блокноте.

Сгенерировать прямо на сервере:

```bash
node -e "console.log(require('crypto').randomBytes(18).toString('base64url'))"
```

**3. Смените пароли учётных записей сотрудников.** Демо-преподаватели (`orlova`, `kim`,
`volkova`) имеют пароль `demo12345` — их надо удалить, а не «оставить на всякий случай»:

```bash
cd /srv/prokod
npm run users                                    # посмотреть, кто заведён
node scripts/manage-users.js --remove orlova
node scripts/manage-users.js --remove kim
node scripts/manage-users.js --remove volkova
```

Сотрудники меняют свои пароли сами: **Профиль → Смена пароля**.

**4. Права на `.env`:**

```bash
chmod 600 /srv/prokod/.env
chown deploy:deploy /srv/prokod/.env
ls -l /srv/prokod/.env      # ожидается -rw------- 1 deploy deploy
```

**5. Никогда не коммитьте `.env`.** Он уже в `.gitignore`. Проверить, что он действительно
игнорируется:

```bash
cd /srv/prokod
git check-ignore -v .env    # должно вывести строку с .gitignore — значит, игнорируется
git status --short          # .env не должен появляться в списке
```

**6. Сохраните `.env` отдельно.** В резервные копии `npm run backup` он **не попадает**
намеренно (там пароли и секрет сессии, класть их в незашифрованный ZIP — плохая идея).
Значит, при полной потере сервера вы восстановите данные, но не настройки. Держите копию
`.env` в менеджере паролей или в зашифрованном хранилище.

**7. Права на данные:**

```bash
sudo chown -R deploy:deploy /srv/prokod
chmod 750 /srv/prokod/data /srv/prokod/backups
```

Владелец должен совпадать с пользователем из systemd-юнита (`User=deploy`). Если запустить
что-нибудь под `sudo` (например, `sudo npm run backup`), файлы получат владельца `root`,
и приложение при следующем старте не сможет писать в базу — получите `SQLITE_CANTOPEN`
или `EACCES`. Лечится тем же `chown -R deploy:deploy`.

<a id="57-мониторинг"></a>

### 5.7 Мониторинг

Задача — узнавать о падении сайта раньше, чем позвонит родитель.

> 💡 **Совет:** отдельного маршрута для проверки состояния (`/healthz`, `/health`)
> в проекте **нет** — это проверено по коду. Для мониторинга используйте главную
> страницу `GET /`: она отдаёт `200 OK` и не требует авторизации. Если хочется
> лёгкой проверки без отдачи 110 КБ HTML, можно запрашивать `HEAD /` или маленький
> статический файл, например `GET /robots.txt`.
>
> **Опциональное улучшение.** Если захотите настоящий health-check, добавьте
> в `server/index.js` перед строкой `app.use('/api', ...)` несколько строк:
>
> ```js
> // Лёгкая проверка живости для мониторинга: не трогает базу и не требует сессии.
> app.get('/healthz', (req, res) => {
>   res.set('Cache-Control', 'no-store').json({ ok: true, uptime: process.uptime() });
> });
> ```
>
> Это правка кода — оформите её коммитом в репозитории, а не на живом сервере.

#### Внешний мониторинг: UptimeRobot

Самый простой вариант. Бесплатный тариф: 50 проверок с интервалом **5 минут**.

1. Регистрация: [uptimerobot.com](https://uptimerobot.com/).
2. **Add New Monitor**:
   - Monitor Type: `HTTPS`;
   - Friendly Name: `ПроКод — лендинг`;
   - URL: `https://prokod.ru/`;
   - Monitoring Interval: `5 minutes`;
   - Alert Contacts: ваша почта, плюс можно подключить Telegram.
3. Добавьте второй монитор на `https://prokod.ru/login` — так вы заметите ситуацию,
   когда nginx жив и отдаёт статику, а Node лежит.
4. Включите **SSL Expiry** — предупреждение, если сертификат не продлился.

**Альтернативы:**

- [Better Stack (Better Uptime)](https://betterstack.com/uptime) — бесплатно 10 мониторов
  с интервалом 3 минуты, красивая страница статуса, эскалации;
- [Healthchecks.io](https://healthchecks.io/) — «мониторинг наоборот»: он ждёт сигнала
  от вашего cron. Идеален для контроля бэкапов (см. [5.8](#58-резервное-копирование)):
  если `npm run backup` не отработал, вы получите письмо;
- [ping-admin.ru](https://ping-admin.ru/) — российский сервис, проверки из РФ.

#### Свой мониторинг: cron + curl + Telegram

Бесплатно и полностью под вашим контролем. Проверяет и сайт, и место на диске.

**Шаг 1. Создайте Telegram-бота.** В Telegram найдите [@BotFather](https://t.me/BotFather),
отправьте `/newbot`, придумайте имя. В ответ придёт токен вида
`7123456789:AAF-xxxxxxxxxxxxxxxxxxxxxxxxxxxxx`.

**Шаг 2. Узнайте свой chat_id.** Напишите боту любое сообщение, затем откройте в браузере:

```
https://api.telegram.org/bot<ВАШ_ТОКЕН>/getUpdates
```

Найдите в ответе `"chat":{"id":123456789`. Это ваш `chat_id`. Для группового чата id
будет отрицательным — это нормально.

**Шаг 3. Скрипт проверки:**

```bash
sudo nano /usr/local/bin/prokod-healthcheck.sh
```

```bash
#!/usr/bin/env bash
# Проверка «ПроКод»: сайт отвечает, служба жива, место на диске есть.
# Уведомления шлются в Telegram. Запускается по cron раз в 5 минут.

set -uo pipefail

# ── Настройки ───────────────────────────────────────────────────────────────
URL="https://prokod.ru/"
SERVICE="prokod"
TG_TOKEN="7123456789:AAF-xxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
TG_CHAT="123456789"
DISK_LIMIT=85            # процент занятого места, после которого предупреждать
STATE_FILE="/var/tmp/prokod-health.state"   # чтобы не спамить одинаковыми сообщениями

notify() {
  # -s тихо, --max-time чтобы не висеть вечно
  curl -s --max-time 15 \
    -X POST "https://api.telegram.org/bot${TG_TOKEN}/sendMessage" \
    -d "chat_id=${TG_CHAT}" \
    -d "parse_mode=HTML" \
    --data-urlencode "text=$1" > /dev/null
}

prev_state=$(cat "$STATE_FILE" 2>/dev/null || echo "ok")
problems=""

# ── 1. Отвечает ли сайт ─────────────────────────────────────────────────────
code=$(curl -s -o /dev/null -w '%{http_code}' --max-time 20 "$URL" || echo "000")
if [ "$code" != "200" ]; then
  problems+="• Сайт отвечает <b>${code}</b> вместо 200%0A"
fi

# ── 2. Жива ли служба ───────────────────────────────────────────────────────
if ! systemctl is-active --quiet "$SERVICE"; then
  problems+="• Служба <b>${SERVICE}</b> не запущена%0A"
fi

# ── 3. Место на диске ───────────────────────────────────────────────────────
used=$(df --output=pcent / | tail -1 | tr -dc '0-9')
if [ "$used" -ge "$DISK_LIMIT" ]; then
  problems+="• Диск занят на <b>${used}%</b> (порог ${DISK_LIMIT}%)%0A"
fi

# ── 4. Свежесть последнего бэкапа (не старше 36 часов) ──────────────────────
newest=$(find /srv/prokod/backups -maxdepth 1 -name 'backup_*.zip' -mtime -1.5 2>/dev/null | head -1)
if [ -z "$newest" ]; then
  problems+="• Свежего бэкапа за последние сутки нет%0A"
fi

# ── Итог ────────────────────────────────────────────────────────────────────
if [ -n "$problems" ]; then
  # Сообщаем только при смене состояния — иначе будет по сообщению каждые 5 минут
  if [ "$prev_state" != "fail" ]; then
    notify "🔴 <b>ПроКод: проблема</b>%0A%0A${problems}%0AСервер: $(hostname)"
    echo "fail" > "$STATE_FILE"
  fi
  exit 1
fi

if [ "$prev_state" = "fail" ]; then
  notify "🟢 <b>ПроКод: всё восстановилось</b>%0AСайт отвечает 200, служба работает."
fi
echo "ok" > "$STATE_FILE"
```

**Шаг 4. Сделайте исполняемым и проверьте вручную:**

```bash
sudo chmod +x /usr/local/bin/prokod-healthcheck.sh
sudo /usr/local/bin/prokod-healthcheck.sh
echo "код возврата: $?"      # 0 — всё хорошо
```

Чтобы проверить, что уведомления доходят, временно остановите службу и запустите скрипт:

```bash
sudo systemctl stop prokod
sudo /usr/local/bin/prokod-healthcheck.sh    # в Telegram должно прийти сообщение
sudo systemctl start prokod
sudo rm -f /var/tmp/prokod-health.state      # сбросить состояние
sudo /usr/local/bin/prokod-healthcheck.sh    # должно прийти «всё восстановилось»
```

**Шаг 5. Поставьте в cron** (от root, чтобы был доступ к `systemctl`):

```bash
sudo crontab -e
```

Добавьте строку:

```
*/5 * * * * /usr/local/bin/prokod-healthcheck.sh >/dev/null 2>&1
```

`*/5 * * * *` означает «каждые 5 минут».

> ⚠️ **Осторожно:** в скрипте лежит токен Telegram-бота. Закройте файл от чужих глаз:
> `sudo chmod 700 /usr/local/bin/prokod-healthcheck.sh`.

#### Журналы: не дать им съесть диск

systemd-journal по умолчанию может занять до 10% диска. На сервере с 20 ГБ это 2 ГБ логов.

```bash
sudo journalctl --disk-usage            # сколько занимают сейчас
sudo journalctl --vacuum-time=30d       # удалить всё старше 30 дней
sudo journalctl --vacuum-size=500M      # или оставить не больше 500 МБ
```

Чтобы ограничение действовало постоянно:

```bash
sudo nano /etc/systemd/journald.conf
```

```ini
[Journal]
SystemMaxUse=500M
MaxRetentionSec=30day
```

```bash
sudo systemctl restart systemd-journald
```

Журналы nginx ротируются сами через `logrotate` (конфиг `/etc/logrotate.d/nginx`),
по умолчанию 14 дней — этого достаточно.

<a id="58-резервное-копирование"></a>

### 5.8 Резервное копирование

> ⚠️ **Осторожно: это самый важный раздел документа.** Сайт можно развернуть заново
> за час. Заявки, карточки учеников с историей, расписание и финансы за два года —
> восстановить неоткуда. Всё это лежит в папке `data/`, и только там.

#### Правило 3-2-1 применительно к проекту

| Правило | Что это значит здесь |
|---|---|
| **3** копии данных | оригинал в `/srv/prokod/data/` + ежедневный архив в `/srv/prokod/backups/` + копия, уехавшая наружу |
| **2** разных носителя | диск сервера + облако (Яндекс.Диск, S3, другой сервер) |
| **1** копия вне площадки | копия **не на том же VPS**. Если провайдер потеряет диск или вы удалите сервер — эта копия останется |

> ⚠️ **Снапшот у провайдера — это не бэкап приложения.** Снапшот копирует диск целиком:
> он спасёт от «сломал систему обновлением», но не от «менеджер случайно удалил карточки
> двадцати учеников неделю назад». Снапшоты обычно перезаписываются по кругу, живут
> на той же площадке и **не проверяют целостность базы**. Делайте и то, и другое:
> снапшот — от аварии сервера, `npm run backup` — от ошибки человека.

#### Что делает `npm run backup`

Штатная команда проекта — используйте её, а не `cp`. Она:

1. **снимает онлайн-снимок базы SQLite** штатным механизмом самой SQLite: собирает
   основной файл и журнал `-wal` в одно согласованное состояние. Останавливать сервер
   не нужно;
2. упаковывает всё содержимое `data/` в ZIP `backups/backup_ГГГГММДД_ЧЧММСС.zip`;
3. кладёт внутрь `manifest.json` с описью: когда снято, сколько файлов, сколько записей
   в каждой коллекции, каким движком;
4. **перечитывает получившийся архив и сверяет контрольные суммы** — про испорченную
   копию вы узнаете сразу, а не в день аварии.

> ⚠️ **Почему нельзя просто скопировать `data/app.sqlite`.** База работает в режиме WAL:
> свежие изменения лежат не в самом файле, а в журнале `app.sqlite-wal` рядом. В README
> приведён реальный замер: база 217 КБ, журнал 828 КБ. Копия одного `app.sqlite`
> потеряла бы бо́льшую часть данных — причём молча, файл будет открываться и выглядеть
> исправным. Подробности механизма: [sqlite.org/wal.html](https://sqlite.org/wal.html).

Полное описание команды, её флагов (`--dir`, `--out`, `--wait`, `--force`) и процедуры
восстановления — в разделе «Резервные копии» [README.md](README.md). Здесь — только
серверная часть.

#### Ежедневный бэкап по cron

Создайте скрипт-обёртку: cron запускается с урезанным `PATH`, и `npm` он может не найти.

```bash
sudo nano /usr/local/bin/prokod-backup.sh
```

```bash
#!/usr/bin/env bash
# Ежедневная резервная копия «ПроКод»: локальный архив + отправка наружу + ротация.

set -uo pipefail

APP_DIR="/srv/prokod"
BACKUP_DIR="$APP_DIR/backups"
KEEP_DAYS=30                     # сколько дней хранить локальные копии
LOG="/var/log/prokod-backup.log"

# cron не знает про nvm и не читает ~/.bashrc — путь к node/npm задаём явно
export PATH="/usr/bin:/usr/local/bin:$PATH"

log() { echo "[$(date '+%Y-%m-%d %H:%M:%S')] $*" >> "$LOG"; }

log "=== Старт резервного копирования ==="

cd "$APP_DIR" || { log "ОШИБКА: нет каталога $APP_DIR"; exit 1; }

# 1. Снять копию. --wait 120: подождать, если рядом уже работает backup/restore
if npm run backup -- --wait 120 >> "$LOG" 2>&1; then
  log "Копия создана"
else
  log "ОШИБКА: npm run backup завершился с кодом $?"
  exit 1
fi

# 2. Имя самого свежего архива
NEWEST=$(ls -1t "$BACKUP_DIR"/backup_*.zip 2>/dev/null | head -1)
if [ -z "$NEWEST" ]; then
  log "ОШИБКА: архив не найден после создания"
  exit 1
fi
log "Свежий архив: $NEWEST ($(du -h "$NEWEST" | cut -f1))"

# 3. Отправить наружу (см. настройку rclone ниже).
#    Раскомментируйте нужный вариант.
# rclone copy "$NEWEST" yadisk:ПроКод/backups --log-file="$LOG" --log-level INFO
# rclone copy "$NEWEST" s3prokod:prokod-backups/ --log-file="$LOG" --log-level INFO
# rsync -az "$NEWEST" backup@BACKUP_HOST:/home/backup/prokod/ >> "$LOG" 2>&1

# 4. Ротация локальных копий: удалить архивы старше KEEP_DAYS дней.
#    Папки prerestore_* НЕ трогаем — это страховка после восстановлений.
DELETED=$(find "$BACKUP_DIR" -maxdepth 1 -name 'backup_*.zip' -mtime +"$KEEP_DAYS" -print -delete | wc -l)
log "Удалено старых копий: $DELETED"

# 5. Сколько места осталось
log "Диск: $(df -h / | tail -1 | awk '{print $4" свободно из "$2}')"
log "=== Готово ==="
```

Сделайте исполняемым, проверьте вручную и поставьте в cron **от пользователя `deploy`**
(чтобы файлы принадлежали ему, а не root):

```bash
sudo chmod +x /usr/local/bin/prokod-backup.sh
sudo touch /var/log/prokod-backup.log
sudo chown deploy:deploy /var/log/prokod-backup.log

# проверка вручную
/usr/local/bin/prokod-backup.sh
tail -20 /var/log/prokod-backup.log
```

Журнал бэкапов пополняется каждую ночь и сам по себе не обрезается. Отдайте его
`logrotate`, как и журналы nginx, — одна команда, и про него можно забыть навсегда:

```bash
sudo tee /etc/logrotate.d/prokod-backup > /dev/null <<'EOF'
/var/log/prokod-backup.log {
    weekly          # проверять раз в неделю
    rotate 8        # хранить 8 старых копий (два месяца)
    compress        # старые сжимать в .gz
    missingok       # нет файла — не ругаться
    notifempty      # пустой не ротировать
    create 0644 deploy deploy   # новый файл создать сразу от нужного владельца
}
EOF

# проверка без реальной ротации
sudo logrotate --debug /etc/logrotate.d/prokod-backup
```

```bash
crontab -e     # БЕЗ sudo — от пользователя deploy
```

```
# Резервная копия «ПроКод» каждый день в 03:30
30 3 * * * /usr/local/bin/prokod-backup.sh
```

> ⚠️ **Осторожно:** не запускайте бэкап через `sudo` и не ставьте его в `sudo crontab -e`.
> Архивы получат владельца `root`, а следующий запуск от `deploy` не сможет их удалить
> при ротации. Хуже: если скрипт когда-нибудь тронет `data/`, приложение потеряет доступ
> к собственной базе.

Проверить, что задание записалось: `crontab -l`.

#### Ротация: чтобы копии не съели диск

Локальную ротацию делает шаг 4 скрипта выше (`find -mtime +30 -delete`). Есть и штатный
механизм проекта, но он привязан к восстановлению:

```bash
npm run restore backup_20260809_033000.zip -- --prune --keep 5
```

Для регулярной чистки удобнее `find` из скрипта.

**Сколько места нужно.** Архив базы школы на 200 учеников — сотни килобайт, максимум
единицы мегабайт (в README приведён пример: 365 КБ данных → 33 КБ архива). 30 копий
займут десятки мегабайт. Даже год ежедневных копий поместится на любом диске. Но следите
за папками `prerestore_*` — они создаются при каждом восстановлении, содержат полное
состояние `data/` и **никогда не удаляются автоматически**, в том числе очисткой `--prune`.
Удаляйте их руками, когда убедились, что восстановление прошло правильно.

#### Выгрузка копий наружу

**Вариант 1: rclone на Яндекс.Диск** (проще всего для российской школы).

```bash
sudo -v ; curl https://rclone.org/install.sh | sudo bash
rclone config
```

Мастер настройки:

- `n` — новый удалённый источник;
- name: `yadisk`;
- Storage: найдите в списке `yandex` (Yandex Disk), введите его номер;
- `client_id`, `client_secret` — оставьте пустыми (Enter);
- Edit advanced config: `n`;
- Use auto config: **`n`** (на сервере нет браузера). rclone выдаст ссылку —
  откройте её на своём компьютере, авторизуйтесь в Яндексе, скопируйте полученный токен
  и вставьте в консоль сервера;
- подтвердите `y`, затем `q` для выхода.

Проверка и первая отправка:

```bash
rclone lsd yadisk:                                  # список папок на Диске
rclone mkdir yadisk:ПроКод/backups
rclone copy /srv/prokod/backups/backup_*.zip yadisk:ПроКод/backups --progress
rclone ls yadisk:ПроКод/backups                     # что уехало
```

Ротация в облаке (удалять копии старше 90 дней):

```bash
rclone delete yadisk:ПроКод/backups --min-age 90d
```

**Вариант 2: S3-совместимое хранилище** (Selectel, Yandex Object Storage, VK Cloud).
Надёжнее и дешевле при больших объёмах, оплата по факту — центы в месяц за наши размеры.

```bash
rclone config
```

- name: `s3prokod`;
- Storage: `s3`;
- provider: `Other`;
- access_key_id / secret_access_key — из панели провайдера;
- endpoint: например `https://s3.storage.selcloud.ru` (Selectel) или
  `https://storage.yandexcloud.net` (Yandex);
- region: `ru-1` (уточните у провайдера).

```bash
rclone copy /srv/prokod/backups/ s3prokod:prokod-backups/ --include "backup_*.zip"
```

> 💡 **Совет:** если хранилище поддерживает **версионирование и блокировку удаления
> (object lock)** — включите. Тогда даже взломщик с доступом к серверу не сможет удалить
> ваши бэкапы. Это защита от шифровальщиков.

**Вариант 3: rsync на другой сервер или домашний компьютер.**

```bash
rsync -az --delete-after \
  /srv/prokod/backups/ backup@BACKUP_HOST:/home/backup/prokod/
```

Для автоматической работы нужен SSH-ключ без passphrase, а на приёмной стороне лучше
ограничить его командой (`command="rsync --server ..."` в `authorized_keys`).

**Контроль, что бэкап реально отработал.** Добавьте в конец скрипта пинг
на [Healthchecks.io](https://healthchecks.io/): заведите там проверку с расписанием
«раз в день», получите URL и допишите:

```bash
curl -fsS --max-time 10 --retry 3 https://hc-ping.com/ВАШ-UUID > /dev/null
```

Если бэкап не отработал — пинга не будет, и сервис пришлёт вам письмо. Это единственный
способ узнать о молча сломавшемся cron.

#### Проверка восстановления — обязательно

> ⚠️ **Осторожно: бэкап, который ни разу не восстанавливали, — не бэкап, а надежда.**
> Проверяйте раз в квартал. Это занимает 15 минут и однажды спасёт школу.

**Как проверить правильно — на отдельной машине, не на боевой.**

Способ А, без второго сервера: разверните копию проекта в другой папке на том же сервере
и восстановите туда.

```bash
# 1. Скопировать код в тестовую папку
sudo mkdir -p /srv/prokod-test && sudo chown deploy:deploy /srv/prokod-test
git clone git@github.com:hhttppss/procode.git /srv/prokod-test
cd /srv/prokod-test
npm ci --omit=dev

# 2. Свой .env с ДРУГИМ портом и своей базой
cp .env.example .env
nano .env       # PORT=3100, TZ=Europe/Moscow, DATABASE_ENGINE=sqlite, TRUST_PROXY=0

# 3. Положить архив и восстановить (сервер тестовой копии не запущен — так и надо)
mkdir -p backups
cp /srv/prokod/backups/backup_20260809_033000.zip backups/
npm run restore backup_20260809_033000.zip
```

Скрипт восстановления сам проверит контрольные суммы, целостность базы
(`PRAGMA integrity_check`), совпадение движка хранения и в конце напечатает
контрольное чтение:

```
  Данные в базе app.sqlite:
    Заявки                 19
    Журнал действий        24
    Расходы                 8
    Занятия               128
    Уведомления            22
    Платежи                32
    Ученики                20
    Сотрудники              5   (администраторов: 2, преподавателей: 3)

  ✓ Восстановление завершено
    Запустите сервер: npm start
```

```bash
# 4. Запустить и посмотреть глазами
npm start
```

Откройте `http://YOUR_SERVER_IP:3100` через SSH-туннель
(`ssh -L 3100:127.0.0.1:3100 deploy@YOUR_SERVER_IP`, затем `http://localhost:3100`
на своём компьютере), войдите и убедитесь, что данные на месте. Потом:

```bash
# 5. Убрать тестовую копию
sudo rm -rf /srv/prokod-test
```

**Чего проверка не покрывает:** файла `.env` в архиве нет. Убедитесь отдельно, что
у вас сохранён актуальный `SESSION_SECRET` и пароль администратора.

**Восстановление на боевом сервере** — когда авария уже случилась:

```bash
sudo systemctl stop prokod          # ОБЯЗАТЕЛЬНО
cd /srv/prokod
npm run restore                     # покажет список копий
npm run restore backup_20260809_033000.zip
sudo systemctl start prokod
sudo systemctl status prokod
```

> ⚠️ **Осторожно:** восстановление при **запущенном** сервере подменяет файл базы
> под работающим процессом. Это надёжный способ испортить данные, и никакие проверки
> скрипта от этого не спасут. Сначала `systemctl stop`, потом restore.

<a id="61-подключение-prokodru-от-покупки-до-замка"></a>

### 6.1 Подключение prokod.ru от покупки до замка

Сквозной сценарий: домена нет вообще, сервер уже настроен по разделам 2 и 3.
Ориентировочное время — час работы плюс ожидание DNS.

**Шаг 1. Проверить, свободен ли домен** (5 минут).

Откройте [reg.ru/domain/new](https://www.reg.ru/domain/new/) (или whois-сервис вроде
[nic.ru/whois](https://www.nic.ru/whois/)) и введите `prokod.ru`. Если занят —
подумайте о вариантах: `prokod-school.ru`, `prokodkids.ru`, `pro-kod.ru`.

> 💡 **Совет:** зону `.ru` для российской школы предпочтительнее `.com` и `.online`:
> она вызывает больше доверия у родителей, лучше индексируется в Яндексе по локальным
> запросам и стоит дешевле в продлении.

**Шаг 2. Купить домен** (15 минут + проверка данных).

Оформите заказ у выбранного регистратора ([4.1](#41-где-покупать-ru-в-2026)),
укажите данные владельца (для школы — ИП или ООО), оплатите, **включите автопродление**.
Дождитесь письма «домен зарегистрирован».

**Шаг 3. Прописать DNS-записи** (5 минут + до 2 часов ожидания).

В панели регистратора → «DNS-записи»:

| Тип | Имя | Значение | TTL |
|---|---|---|---|
| `A` | `@` | `YOUR_SERVER_IP` | 3600 |
| `A` | `www` | `YOUR_SERVER_IP` | 3600 |

Удалите «парковочные» записи регистратора, если они там есть (обычно A-запись на их
заглушку). Ждите и проверяйте:

```bash
nslookup prokod.ru
```

Пока не увидите свой IP — дальше не идите.

**Шаг 4. Настроить nginx на домен** (5 минут).

```bash
sudo nano /etc/nginx/sites-available/prokod
```

Убедитесь, что в `server_name` стоит `prokod.ru www.prokod.ru`. Примените:

```bash
sudo nginx -t && sudo systemctl reload nginx
curl -I http://prokod.ru/       # ожидается 200 OK от приложения
```

**Шаг 5. Выпустить сертификат** (3 минуты).

```bash
sudo certbot --nginx -d prokod.ru -d www.prokod.ru
sudo certbot renew --dry-run
```

Откройте `https://prokod.ru` — **зелёный замок**. Готово.

**Шаг 6. Что поменять в коде** (10 минут).

Если ваш домен отличается от `prokod.ru`, замените его в файлах из
[4.6](#46-заменить-домен-в-коде): `public/index.html` (canonical, Open Graph,
Twitter-карточка, JSON-LD), `public/robots.txt`, `public/sitemap.xml`.

Правки делайте **в репозитории** локально, потом:

```bash
cd /srv/prokod
git pull
sudo systemctl restart prokod    # ОБЯЗАТЕЛЬНО: пересчитать хэши CSP
```

**Шаг 7. Добить редиректы и HSTS** (10 минут).

Добавьте блок редиректа с `www` ([4.5](#45-проверка-https-и-www)) и, когда убедитесь,
что HTTPS стабилен и `certbot renew --dry-run` проходит, — заголовок HSTS
([5.1](#51-боевой-конфиг-nginx)).

**Шаг 8. Сказать поисковикам** (15 минут).

- [Яндекс.Вебмастер](https://webmaster.yandex.ru/) — добавьте сайт, подтвердите права
  (проще всего HTML-файлом в `public/` или мета-тегом), укажите главное зеркало
  (`https://prokod.ru` без `www`), отправьте `https://prokod.ru/sitemap.xml`.
- [Google Search Console](https://search.google.com/search-console) — то же самое.
- [Яндекс.Метрика](https://metrika.yandex.ru/) — счётчик посещаемости.

> ⚠️ **Осторожно со счётчиками и Content-Security-Policy.** В приложении политика CSP
> строгая, без `unsafe-inline` (`server/csp.js`). Код Яндекс.Метрики или Google Analytics
> просто вставить в HTML **не получится — браузер его заблокирует**. Нужно:
>
> 1. добавить домен счётчика в директивы `script-src` и `connect-src`
>    (для Метрики: `https://mc.yandex.ru`), а для картинки-пикселя — в `img-src`;
> 2. инлайновую часть кода счётчика либо вынести в отдельный файл в `public/js/`,
>    либо посчитать её sha256 и добавить в политику — механизм для этого уже есть,
>    он используется для микроразметки лендинга;
> 3. перезапустить сервер.
>
> Это правка `server/csp.js`. Не «отключайте CSP, чтобы заработал счётчик» —
> вы снимете защиту от XSS ради статистики.

**Шаг 9. Прогнать чек-лист приёмки** — [раздел 7](#7-чек-лист-приёмки).

### 6.2 Почта на домене

**Сначала честно: в проекте почтовых уведомлений нет.** Это прямо написано в разделе
«Известные ограничения» [README.md](README.md): уведомления живут только внутри интерфейса,
страница опрашивает сервер раз в 30 секунд, письма и мессенджеры не подключены. О новой
заявке администратор узнаёт из колокольчика в шапке платформы, а сама заявка дополнительно
печатается в консоль сервера (то есть попадает в `journalctl -u prokod`).

Значит, почта нужна не приложению, а вам: адрес `info@prokod.ru` в футере лендинга,
переписка с родителями, восстановление паролей от сервисов.

#### Почему нельзя слать письма прямо с VPS

Соблазн понятный: поставить `postfix` и отправлять через `sendmail`. Не делайте так.

1. **Порт 25 закрыт.** Практически все хостинг-провайдеры (и российские, и зарубежные)
   блокируют исходящий порт 25 на новых серверах, чтобы через них не рассылали спам.
   Открывают по заявке, и то не всем.
2. **Письма уйдут в спам, даже если порт откроют.** IP-адрес нового VPS не имеет
   репутации, часто состоит в «пуле хостинга», а иногда уже занесён в чёрные списки
   предыдущим владельцем. Gmail, Яндекс и Mail.ru такие письма либо кладут в спам,
   либо молча выбрасывают.
3. **Нужен полный комплект настроек** — обратная DNS-запись (PTR), SPF, DKIM, DMARC,
   валидный HELO. Настроить их правильно сложнее, чем весь этот документ, а сломать
   репутацию домена — легко и надолго.
4. **Свой почтовый сервер надо администрировать**: обновления, антиспам, хранилище,
   бэкапы ящиков. Это отдельная работа.

**Правильное решение: почта у специализированного провайдера.**

#### Варианты для российской школы

| **Яндекс 360 для бизнеса** | есть бесплатный тариф на несколько ящиков; платные от ~250 ₽/пользователь/мес | Самый популярный выбор в РФ. Знакомый интерфейс, мобильные приложения, Диск и Документы в комплекте | [360.yandex.ru/business](https://360.yandex.ru/business/) |
| **Mail.ru для бизнеса** | бесплатный тариф, платные от ~200 ₽/пользователь | Аналогично, часть экосистемы VK | [biz.mail.ru](https://biz.mail.ru/) |
| **VK WorkSpace** | от ~300 ₽/пользователь | Почта + мессенджер + календарь + звонки. Для школы с несколькими сотрудниками может заменить сразу три сервиса | [biz.mail.ru/workspace](https://biz.mail.ru/workspace/) |

#### Настройка на примере Яндекс 360

**Шаг 1.** Зарегистрируйтесь на [360.yandex.ru/business](https://360.yandex.ru/business/),
добавьте домен `prokod.ru`.

**Шаг 2. Подтвердите владение доменом.** Яндекс предложит один из способов; самый простой —

| Тип | Имя | Значение |
|---|---|---|
| `TXT` | `@` | `yandex-verification: a1b2c3d4e5f6` |

Добавьте её в DNS у регистратора и нажмите «Проверить» — обычно проходит за 10–30 минут.

**Шаг 3. MX-записи** — куда доставлять почту для `@prokod.ru`:

| Тип | Имя | Значение | Приоритет | TTL |
|---|---|---|---|---|
| `MX` | `@` | `mx.yandex.net.` | 10 | 3600 |

> ⚠️ **Осторожно:** удалите все прежние MX-записи (регистраторы часто прописывают свои
> заглушки). Две группы MX-записей от разных провайдеров = потерянные письма.
> И не забывайте точку в конце `mx.yandex.net.` — некоторые панели без неё дописывают
> ваш домен и получается `mx.yandex.net.prokod.ru`.

**Шаг 4. SPF** — говорит принимающим серверам, кому разрешено слать письма от вашего имени:

| Тип | Имя | Значение | TTL |
|---|---|---|---|
| `TXT` | `@` | `v=spf1 redirect=_spf.yandex.net` | 3600 |

Разбор: `v=spf1` — версия, `redirect=_spf.yandex.net` — «спроси у Яндекса список
разрешённых серверов».

Если писем нет ни от кого, кроме Яндекса, строгий вариант:
`v=spf1 include:_spf.yandex.net ~all`, где `~all` означает «остальное — подозрительно».

> ⚠️ **Осторожно:** `TXT`-запись SPF для домена должна быть **ровно одна**. Две записи,
> начинающиеся с `v=spf1`, — это ошибка, и проверка проваливается целиком. Если добавляете
> второй сервис (например, рассылку), включайте его в существующую запись через `include:`,
> а не отдельной строкой.

**Шаг 5. DKIM** — криптографическая подпись писем. Яндекс сгенерирует ключ в панели
администратора («Почта для домена» → «DKIM-подпись»), вы копируете значение в DNS:

| Тип | Имя | Значение | TTL |
|---|---|---|---|
| `TXT` | `mail._domainkey` | `v=DKIM1; k=rsa; p=MIGfMA0GCSqGSIb3DQEB...` (длинная строка от Яндекса) | 3600 |

Селектор (`mail`) может отличаться — берите точно тот, что показала панель.

**Шаг 6. DMARC** — что делать с письмами, не прошедшими SPF и DKIM, и куда слать отчёты:

| Тип | Имя | Значение | TTL |
|---|---|---|---|
| `TXT` | `_dmarc` | `v=DMARC1; p=none; rua=mailto:postmaster@prokod.ru; pct=100` | 3600 |

Разбор политики:

| Параметр | Значение | Смысл |
|---|---|---|
| `p=none` | ничего не делать | **начните с этого**: только собирать отчёты, письма не блокируются |
| `p=quarantine` | в спам | следующий шаг, через 2–4 недели наблюдения |
| `p=reject` | отклонять | финальная строгая политика, когда уверены, что всё настроено |
| `rua=mailto:` | адрес для отчётов | приходят сводки: кто и откуда слал письма от вашего имени |
| `pct=100` | процент писем | к скольким письмам применять политику |

> ⚠️ **Осторожно:** не ставьте `p=reject` сразу. Если какой-то сервис (например, форма
> обратной связи на другом сайте или бухгалтерская программа) шлёт письма от вашего домена
> и не учтён в SPF, при `reject` они начнут пропадать без следа. Месяц на `p=none`,
> изучение отчётов, потом ужесточение.

**Шаг 7. Проверка.** Через 1–2 часа после добавления записей:

```bash
dig +short MX prokod.ru
dig +short TXT prokod.ru
dig +short TXT mail._domainkey.prokod.ru
dig +short TXT _dmarc.prokod.ru
```

И обязательно — сквозная проверка: отправьте письмо с нового ящика на
[mail-tester.com](https://www.mail-tester.com/) (сервис даёт временный адрес и оценку
от 0 до 10) или на [check-auth@verifier.port25.com](mailto:check-auth@verifier.port25.com)
(пришлёт подробный отчёт по SPF/DKIM/DMARC). Цель — 9–10 из 10.

#### Транзакционные письма — на будущее

Если однажды понадобится, чтобы платформа сама отправляла письма (уведомление родителю
о занятии, «спасибо за заявку», восстановление пароля), правильный путь — **SMTP-релей**,
а не свой почтовый сервер:

| Сервис | Бесплатный лимит | Комментарий |
|---|---|---|
| [Unisender Go](https://go.unisender.ru/) | есть стартовый тариф | Российский, хорошая доставляемость в РФ |
| [Sendsay](https://sendsay.ru/) | по тарифу | Российский, транзакционные и массовые рассылки |
| [Mailopost](https://mailopost.ru/) | по тарифу | Российский, простое API |
| [Resend](https://resend.com/) | 3 000 писем/мес | Зарубежный, современный API, простая интеграция |
| [Postmark](https://postmarkapp.com/) | 100 писем/мес | Зарубежный, лучшая репутация по транзакционным письмам |

Интеграция потребует правки кода: добавить зависимость (`nodemailer` или HTTP-вызов

не делать отправку синхронной в обработчике запроса, чтобы медленный SMTP не тормозил
приём заявки. Пока такой задачи нет, ничего ставить не нужно.

<a id="63-три-способа-снять-копию-базы"></a>

### 6.3 Три способа снять копию базы

Иногда нужно снять именно базу, а не весь `data/`, — например, чтобы посмотреть данные
локально. Вот три корректных способа и один неправильный.

**Способ 1 (основной): `npm run backup`.**

```bash
cd /srv/prokod
npm run backup
```

Штатный механизм проекта: онлайн-снимок базы + вся папка `data/` + `manifest.json`
с описью + проверка контрольных сумм. Сервер останавливать не нужно. Это то, что должно
стоять в cron. Все флаги — в README.

**Способ 2: `sqlite3 .backup`.**

Штатная команда SQLite для «горячего» копирования: она читает базу вместе с журналом WAL
и записывает согласованное состояние.

```bash
sqlite3 /srv/prokod/data/app.sqlite ".backup '/tmp/app-copy.sqlite'"
ls -lh /tmp/app-copy.sqlite
sqlite3 /tmp/app-copy.sqlite "PRAGMA integrity_check;"     # ожидается ok
```

Годится, когда нужен именно один файл базы, без остальной папки.

**Способ 3: `VACUUM INTO`.**

Появился в SQLite 3.27. Делает то же самое, что `.backup`, но заодно **дефрагментирует**
базу: результат компактнее оригинала.

```bash
sqlite3 /srv/prokod/data/app.sqlite "VACUUM INTO '/tmp/app-compact.sqlite';"
ls -lh /srv/prokod/data/app.sqlite /tmp/app-compact.sqlite
```

Удобно, когда база разрослась после массовых удалений: свободные страницы возвращаются
операционной системе. Полезно раз в несколько месяцев, но не вместо бэкапа.

**❌ Как делать НЕЛЬЗЯ: `cp app.sqlite`.**

```bash
# ТАК НЕ ДЕЛАТЬ ПРИ ЗАПУЩЕННОМ СЕРВЕРЕ
cp /srv/prokod/data/app.sqlite /tmp/backup.sqlite
```

> ⚠️ **Осторожно:** база работает в режиме **WAL** (Write-Ahead Logging). Свежие
> изменения сначала пишутся в отдельный файл журнала `app.sqlite-wal` и только потом,
> в момент «чекпойнта», переносятся в основной файл. В README проекта приведён реальный
> замер: `app.sqlite` — 217 КБ, `app.sqlite-wal` — 828 КБ. То есть **бо́льшая часть
> недавних данных была в журнале**, а не в базе.
>
> Простое копирование `app.sqlite` даст вам файл, который откроется, покажет старые данные
> и будет выглядеть совершенно исправным. Вы обнаружите пропажу в тот день, когда
> восстановитесь из этой «копии».
>
> Копировать `app.sqlite` вместе с `-wal` и `-shm` тоже плохая идея: файлы снимаются
> не в один момент, состояние может не сойтись. Именно поэтому скрипт `npm run backup`
> кладёт в архив **снимок**, а файлы `-wal` и `-shm` намеренно не включает.
>
> Копировать `app.sqlite` **можно** только при полностью остановленном сервере — тогда
> SQLite при закрытии переносит журнал в основной файл и удаляет `-wal`/`-shm`.
> Но проще и безопаснее использовать `npm run backup`.

Подробнее о WAL: [sqlite.org/wal.html](https://sqlite.org/wal.html),
о резервном копировании: [sqlite.org/backup.html](https://sqlite.org/backup.html).

## 7. Что делать после установки — чек-лист приёмки

Пройдите список сверху вниз **до того**, как дадите ссылку родителям. Каждый пункт —
конкретное действие с проверяемым результатом.

### Доступность и HTTPS

- [ ] **Сайт открывается по `https://prokod.ru`** — есть замок, нет предупреждений браузера.
- [ ] **`http://prokod.ru` редиректит на HTTPS** — `curl -I http://prokod.ru/` даёт `301`.
- [ ] **`www.prokod.ru` ведёт на основной домен** — `curl -I https://www.prokod.ru/` даёт `301`.
- [ ] **Порт 3000 снаружи закрыт** — `curl -m 5 http://YOUR_SERVER_IP:3000/` со своего
      компьютера завершается таймаутом.
- [ ] **Оценка SSL не ниже A** — [ssllabs.com/ssltest](https://www.ssllabs.com/ssltest/).
- [ ] **Автопродление сертификата работает** — `sudo certbot renew --dry-run` завершается
      «all simulated renewals succeeded».
- [ ] **Подделать свой IP нельзя** — самая незаметная дыра из всех. Выполните
      `curl -s -H 'X-Forwarded-For: 1.2.3.4' https://prokod.ru/ -o /dev/null`, затем
      посмотрите `sudo journalctl -u prokod -n 20`. Адрес `1.2.3.4` в записях появиться
      **не должен**. Если появился — в nginx стоит `$proxy_add_x_forwarded_for` вместо
      `$remote_addr`, и все ограничения по IP (включая защиту от перебора пароля)
      обходятся одной строкой заголовка. См. [3.5](#35-файл-env-для-продакшена).

### Работа приложения

- [ ] **Лендинг открывается и выглядит правильно** — стили загрузились, шрифты не
      «системные». Если вёрстка «поехала» — на сервере старый `public/css/styles.css`:
      соберите CSS локально (`npm run css`), закоммитьте и обновитесь.
- [ ] **В консоли браузера (F12) нет ошибок CSP.** Если есть `Refused to execute inline
      script` — вы правили HTML и не перезапустили службу.
- [ ] **Вход в платформу работает** — `https://prokod.ru/login`, ваш логин и пароль,
      попадаете в `/app`.
- [ ] **Заявка с лендинга долетает** — заполните форму настоящими данными на реальном
      телефоне, затем проверьте: заявка появилась в модуле «Заявки» со статусом «Новая»,
      и в шапке загорелся колокольчик.
- [ ] **Заявка видна в журнале сервера** — `sudo journalctl -u prokod -n 30` показывает
      обращение (приложение печатает каждую новую заявку в консоль).
- [ ] **Уведомление появилось** — колокольчик в шапке платформы. Напоминание: почтовых
      и мессенджер-уведомлений в проекте нет, это ожидаемое поведение.
- [ ] **Роли работают** — зайдите под преподавателем: в меню нет «Заявок», «Финансов»
      и «Сотрудников», в карточке ученика нет контактов родителей.
- [ ] **Выгрузка в CSV открывается** — «Заявки» → экспорт, файл скачивается и корректно
      открывается в Excel (кириллица не превратилась в кракозябры).

### Время и данные

- [ ] **Часовой пояс верный** — `sudo journalctl -u prokod | grep "Часовой пояс"`
      показывает `Europe/Moscow`. Дополнительно: создайте занятие на конкретное время
      и убедитесь, что оно отображается именно так, а не на три часа раньше.
- [ ] **Сегодняшний день подсвечен правильно** в расписании (вид «Месяц»).
- [ ] **Демо-данные удалены** — если разворачивали с `npm run seed`, выполните
      `npm run seed:reset` (только на пустом проекте!) и удалите демо-преподавателей
      `orlova`, `kim`, `volkova`.
- [ ] **Пароли сменены** — `ADMIN_PASSWORD` в `.env` не `procode2025`; сервер при старте
      не печатает блок `⚠ ВНИМАНИЕ`.
- [ ] **`SESSION_SECRET` задан** — проверка: `sudo systemctl restart prokod`, после
      перезапуска вы **остаётесь** залогинены в платформе (страница не выкинула на вход).

### Надёжность

- [ ] **Автозапуск переживает перезагрузку** — `sudo reboot`, через минуту
      `sudo systemctl status prokod` показывает `active (running)`, а сайт открывается.
- [ ] **Процесс ровно один** — `ps aux | grep "[n]ode"` даёт **одну** строку
      с `server/index.js`.
- [ ] **Бэкап отработал** — `npm run backup` создал архив, в выводе «✓ Бэкап создан»
      и «контрольные суммы совпали».
- [ ] **Архив реально распаковывается** — `unzip -l backups/backup_*.zip` показывает
      `manifest.json` и файлы из `data/`. А лучше — прогоните полную проверку
      восстановления из [5.8](#58-резервное-копирование).
- [ ] **Cron бэкапа стоит** — `crontab -l` показывает строку с `prokod-backup.sh`.
      На следующий день проверьте, что появился свежий архив.
- [ ] **Копия уезжает наружу** — `rclone ls yadisk:ПроКод/backups` (или ваш вариант)
      показывает сегодняшний файл.
- [ ] **`.env` сохранён отдельно** — копия в менеджере паролей. Его нет ни в git,
      ни в бэкапах.
- [ ] **Мониторинг прислал тестовое уведомление** — остановите службу на минуту
      и убедитесь, что UptimeRobot (или ваш скрипт) написал вам.
- [ ] **Файрвол включён** — `sudo ufw status` показывает `Status: active` и только
      порты 22, 80, 443.
- [ ] **fail2ban работает** — `sudo fail2ban-client status` показывает активные правила.
- [ ] **Свободного места достаточно** — `df -h` показывает не меньше 30% свободного.

### Содержание сайта и юридическая часть

## 8. Частые ошибки

Таблица «симптом → причина → решение». Ищите свой симптом в первой колонке.

| # | Симптом | Причина | Решение |
|---|---|---|---|
| 1 | **502 Bad Gateway** от nginx | Приложение не запущено, упало или слушает не тот порт | `sudo systemctl status prokod` → если `failed`, смотреть `sudo journalctl -u prokod -n 50`. Проверить, что `PORT` в `.env` совпадает с `proxy_pass` в nginx. Проверить, что процесс слушает: `ss -tulpn \| grep 3000` |
| 2 | **504 Gateway Timeout** | Приложение живо, но не отвечает за отведённое время: тяжёлый запрос или зависание на записи в базу | Увеличить `proxy_read_timeout`. Посмотреть нагрузку (`top`) и место на диске (`df -h`) — при 100% заполнения SQLite подвисает на записи |
| 3 | **Сайт открывается по `http://IP:3000`** в обход nginx и HTTPS | Приложение слушает все интерфейсы (`app.listen(config.port)` без адреса), файрвол не настроен | Настроить `ufw` ([5.3](#53-файрвол-ufw)). Дополнительно — привязать к `127.0.0.1` правкой одной строки в `server/index.js` ([3.9](#39-nginx-как-обратный-прокси)) |
| 4 | **«Слишком много запросов» у всех подряд.** Родители не могут отправить форму, сотрудники — войти | Забыли `TRUST_PROXY=1` за nginx. Приложение видит всех как `127.0.0.1` и считает лимиты на «одного посетителя» | В `.env` поставить `TRUST_PROXY=1`, `sudo systemctl restart prokod`. Убедиться, что nginx передаёт `X-Forwarded-For` ([3.9](#39-nginx-как-обратный-прокси)) |
| 5 | **Ограничения по IP не работают вовсе**, перебор пароля возможен | `TRUST_PROXY=1` **без** прокси: заголовок `X-Forwarded-For` подделывается клиентом | Если Node смотрит в интернет напрямую — `TRUST_PROXY=0`. Лучше — поставить nginx |
| 5а | **То же, но nginx стоит и всё «выглядит правильно»**: снаружи защиты нет, изнутри лимиты как будто работают | В nginx написано `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` — оно **дописывает** к заголовку клиента, а Express берёт самое левое значение | Заменить на `proxy_set_header X-Forwarded-For $remote_addr;` во **всех** `location`, `sudo nginx -t && sudo systemctl reload nginx`. Проверка — в [3.5](#35-файл-env-для-продакшена) |
| 5б | **`nginx -t` пишет `unknown directive "http2"`**, сайт по HTTPS не поднимается | Конфиг взят из статьи под nginx 1.25.1+, а в Ubuntu 24.04 штатный nginx 1.24 | Убрать строку `http2 on;` и включить HTTP/2 параметром: `listen 443 ssl http2;`. Версия — `nginx -v` |
| 6 | **Время на три часа назад.** Занятие в 10:00 показывается в 07:00, зарплата попала в чужой месяц | VPS живёт в UTC, `TZ` не задан | В `.env` добавить `TZ=Europe/Moscow`, на сервере — `sudo timedatectl set-timezone Europe/Moscow`, перезапустить службу. Проверка: в журнале старта строка `Часовой пояс: Europe/Moscow` |
| 7 | **`Error: Cannot find module '.../better_sqlite3.node'` или `ERR_DLOPEN_FAILED`** при старте | Нативный модуль не собрался или собран под другую платформу | Установить `build-essential` и `python3`, затем `npm rebuild better-sqlite3`. Не помогло — временно `DATABASE_ENGINE=json` в `.env` ([3.4](#34-установка-зависимостей)) |
| 8 | **`NODE_MODULE_VERSION mismatch`**: «was compiled against a different Node.js version» | Обновили Node (например, с 20 на 22), а модуль остался собранным под старую версию | `cd /srv/prokod && npm rebuild better-sqlite3 && sudo systemctl restart prokod`. Надёжнее: `rm -rf node_modules && npm ci --omit=dev` |
| 9 | **`SQLITE_BUSY: database is locked`** | Запущено **два процесса** на одну базу: старый `npm start` в забытой сессии `screen`/`tmux` + служба, либо PM2 в cluster-режиме | `ps aux \| grep "[n]ode"` — должна быть **одна** строка. Лишнее убить. PM2: `pm2 describe prokod` → `exec mode` должен быть `fork_mode`. См. предупреждение в [3.7](#37-автозапуск-systemd) |
| 10 | **Данные «мигают»**: сохранил ученика — исчез, обновил — появился | Два процесса с независимыми кэшами коллекций в памяти | То же, что в пункте 9: оставить один процесс |
| 11 | **Вылетает из платформы после каждого рестарта** службы | `SESSION_SECRET` не задан или оставлена заглушка — при старте генерируется случайный, все cookie становятся недействительными | Сгенерировать: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`, вписать в `.env`, перезапустить |
| 12 | **Скрипт заблокирован CSP** после правки HTML. В консоли браузера: `Refused to execute inline script because it violates CSP` | Хэши инлайновых блоков считаются **один раз при старте сервера** (`server/csp.js`). Правили `public/index.html` — сервер об этом не знает | `sudo systemctl restart prokod`. Это обязательный шаг любого деплоя, где менялась разметка |
| 13 | **Микроразметка пропала из Яндекс.Вебмастера** после обновления | То же самое: блоки `<script type="application/ld+json">` заблокированы CSP | `sudo systemctl restart prokod`, затем перепроверить в валидаторе разметки |
| 14 | **Сертификат не продлился**, браузер ругается на просроченный | Certbot не смог пройти проверку: nginx перехватывает `/.well-known/acme-challenge/`, домен переехал, или таймер выключен | `sudo certbot renew --dry-run` покажет причину. Проверить `systemctl list-timers \| grep certbot`. В nginx оставить `location /.well-known/acme-challenge/ { root /var/www/html; }` в HTTP-блоке |
| 15 | **`ERR_TOO_MANY_REDIRECTS`** | Обычно Cloudflare в режиме `Flexible SSL` плюс редирект «HTTP→HTTPS» на вашем nginx: получается цикл | В Cloudflare переключить SSL на **`Full (strict)`** ([4.4](#44-cloudflare-честный-разбор)). Без Cloudflare — проверить, что редирект не ссылается сам на себя |
| 16 | **Закончилось место на диске.** Сайт лежит, запись в базу падает | Журналы systemd, журналы nginx, папка `backups/` без ротации, папки `prerestore_*` | `df -h`, затем `du -sh /srv/prokod/* /var/log/*`. Почистить: `sudo journalctl --vacuum-time=30d`, удалить старые архивы, настроить ротацию ([5.8](#58-резервное-копирование)) |
| 17 | **`SQLITE_CANTOPEN` или `EACCES: permission denied`** при записи | Владелец файлов в `data/` не совпадает с пользователем службы. Обычно после запуска чего-нибудь через `sudo` | `sudo chown -R deploy:deploy /srv/prokod`, `sudo systemctl restart prokod`. Никогда не запускайте `npm` в проекте через `sudo` |
| 18 | **Служба не стартует:** `Failed to set up mount namespacing ... No such file or directory` | В systemd-юните `ReadWritePaths=` указывает на несуществующие папки (`data/`, `backups/` не приехали из git) | `mkdir -p /srv/prokod/data /srv/prokod/backups`, `sudo systemctl start prokod` |
| 19 | **Потеряли `.env`** при переустановке сервера | Файл в `.gitignore` и **не попадает в бэкапы** — это сделано намеренно, там пароли и секрет | Создать заново из `.env.example`. Сгенерировать новый `SESSION_SECRET` (все текущие сессии сбросятся — это нормально). На будущее: хранить копию в менеджере паролей |
| 20 | **После `npm run restore` данные не появились** или база пустая | Восстановление выполнено **при запущенном сервере** — работающий процесс переписал файл своим состоянием. Либо копия снята на другом `DATABASE_ENGINE` | Остановить службу (`sudo systemctl stop prokod`), повторить восстановление, потом запустить. Данные «до» лежат в `backups/prerestore_*` |
| 21 | **`git pull` отказывается работать:** «Your local changes would be overwritten» | Файлы правили прямо на сервере (например, `public/index.html` или конфиг) | Посмотреть, что изменилось: `git status`, `git diff`. Нужное — перенести в репозиторий и закоммитить нормально. Ненужное — откатить: `git checkout -- <файл>`. Правило: сервер только забирает код, правки делаются в репозитории |
| 22 | **Двойное сжатие:** ответ сжат дважды или битый контент | `gzip on` в nginx **и** middleware `compression` в приложении | Оставить один слой: либо `gzip off` в nginx (по умолчанию), либо убрать `app.use(compression())` из `server/index.js`. Проверка: в ответе ровно один `content-encoding: gzip` ([5.2](#52-двойное-сжатие)) |
| 23 | **Забыли заменить домен** — в поиске и соцсетях ссылки ведут на `prokod.ru`, а сайт на другом адресе | Домен захардкожен в `canonical`, Open Graph, `robots.txt`, `sitemap.xml` | `grep -rn "prokod.ru" /srv/prokod/public/` — заменить везде в репозитории, `git pull` на сервере, **перезапустить службу** ([4.6](#46-заменить-домен-в-коде)) |
| 24 | **Вёрстка «поехала»**, стили не применяются к новым блокам | На сервере старый `public/css/styles.css`: Tailwind собирает только те классы, что нашёл в исходниках | Локально: `npm run css`, закоммитить изменённый `styles.css`, `git push`. На сервере: `git pull` + рестарт. Собирать CSS на сервере не нужно и при `--omit=dev` невозможно ([3.4](#34-установка-зависимостей)) |
| 25 | **`tailwindcss: not found`** при попытке `npm run css` на сервере | `npm ci --omit=dev` не ставит devDependencies, а Tailwind — именно devDependency | Не собирать CSS на сервере. Файл `public/css/styles.css` уже в репозитории — он приезжает с кодом |
| 26 | **`EADDRINUSE: порт 3000 уже занят`** | Другой экземпляр приложения уже работает (забытая сессия, PM2 и systemd одновременно) | `ss -tulpn \| grep 3000` — увидеть, кто занял. Оставить один способ автозапуска: либо systemd, либо PM2 |
| 27 | **Запросы к API возвращают ошибку про Origin** при работе через прокси | nginx не передаёт `Host`, приложение считает запрос межсайтовым (`server/auth.js` проверяет `Origin`) | Добавить `proxy_set_header Host $host;` в блок `location` ([3.9](#39-nginx-как-обратный-прокси)) |
| 28 | **«Показаны свежие 200 заявок»**, старых не видно | Так и задумано: список заявок отдаётся порциями по 200, чтобы страница не разрасталась бесконечно | Пользоваться поиском и фильтром по датам. Чтобы забрать **всё** — выгрузка в CSV, она не обрезается |
| 29 | **`npm ci` падает с `Killed`** | Кончилась память при сборке нативного модуля | Сделать swap-файл ([2.8](#28-swap-файл)) и повторить |
| 30 | **Не пускает по SSH после настройки** | Отключили парольный вход, а ключ не скопирован; или ufw включён без `allow OpenSSH` | Зайти через **KVM-консоль** в панели провайдера, вернуть `PasswordAuthentication yes` или добавить ключ, `sudo ufw allow OpenSSH`. Отсюда правило: всегда проверять новый способ входа во втором окне, не закрывая рабочее |
