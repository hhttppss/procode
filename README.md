# ПроКод — сайт и внутренняя платформа школы

Лендинг для родителей + внутренняя CRM для школы: заявки, ученики, преподаватели,
расписание и финансы. Работает локально одной командой, без базы данных и внешних сервисов.

- **Лендинг** — <http://localhost:3000/>
- **Платформа** — <http://localhost:3000/app>
- **Вход для сотрудников** — <http://localhost:3000/login>

> Подробная пошаговая инструкция по запуску, включая решение частых проблем, —
> в отдельном файле [**ЗАПУСК.md**](ЗАПУСК.md).

## Быстрый старт

Нужен [Node.js](https://nodejs.org/) версии 18 или новее (проверено на 24).

```bash
cd D:\ProCode

npm install        # поставить зависимости (один раз)
npm run css        # собрать стили в public/css/styles.css
npm run seed       # демо-данные: ученики, расписание, финансы, преподаватели
npm start          # запустить сервер
```

Откройте <http://localhost:3000/>. Чтобы остановить сервер — `Ctrl + C` в терминале.

**Вход в платформу.** Заведены две учётные записи администратора:

| Логин | Кому | Роль |
|---|---|---|
| `Yarichpek375` | владелец | Администратор |
| `89606225073n.` | менеджер | Администратор |

Регистр логина не важен: `yarichpek375` тоже подойдёт. Действующие пароли —
в файле [ЗАПУСК.md](ЗАПУСК.md), раздел 3; после первого входа смените их в разделе
**Профиль → Смена пароля**.

Команда `npm run seed` дополнительно создаёт трёх демо-преподавателей — `orlova`, `kim`,
`volkova`, пароль у всех `demo12345`. Под ними удобно посмотреть, как выглядит система
для роли «Преподаватель». Перед выходом «в бой» их стоит удалить.

## Роли и права

Ролей три. «Управляющий школы» ведёт ежедневную работу — заявки, учеников, расписание
и деньги, — но не распоряжается сотрудниками: всё, что касается учётных записей и того,
сколько платят сотруднику, остаётся за администратором.

| Что | Администратор | Управляющий школы | Преподаватель |
|---|---|---|---|
| Заявки с сайта | полный доступ | полный доступ | нет доступа |
| Ученики | полный CRUD, все поля | полный CRUD, все поля | только свои, только просмотр |
| Контакты родителей, оплаты, заметки администрации | видит | видит | **не видит** |
| Закрепление ученика за преподавателем | назначает | **не назначает** | нет доступа |
| Расписание | создаёт, переносит, удаляет | создаёт, переносит, удаляет | видит своё, отмечает итог занятия |
| Финансы | полный доступ | полный доступ | нет доступа |
| Модуль «Сотрудники» | полный доступ | **нет доступа** | нет доступа |
| Ставки и оклады сотрудников | назначает | **не меняет** | не видит |
| Учётные записи: создание, роль, пароль | да | **нет** | нет |
| Свой профиль | правит, включая пароль | правит, включая пароль | **только читает** |

Преподаватель не меняет ни свои личные данные, ни пароль: учётной записью полностью
распоряжается администратор. Управляющий видит имя преподавателя в карточке ученика
и выбирает преподавателя при составлении расписания — без этого занятие не создать, —
но сменить закрепление ученика не может.

Разграничение сделано на трёх уровнях, а не только скрытием кнопок:

1. **Маршруты страниц** (`server/routes/pages.js`) — преподаватель, открыв `/app/finance`,
   получает переадресацию на главную. В его HTML нет и самих ссылок на закрытые разделы.
   То же и с управляющим на `/app/teachers`.
2. **Маршруты API** (`server/routes/api/index.js`) — «Заявки» и «Финансы» открыты
   администратору и управляющему, «Сотрудники» — только администратору. Прямой запрос
   от того, кому раздел закрыт, вернёт `403`.
3. **Поля ответа** (`server/domain/access.js`) — телефон родителя, история оплат, заметки
   администратора, ставка и оклад **физически отсутствуют** в JSON, который получает преподаватель.
   Выборки тоже строятся по `req.user.id`, а не по идентификатору из запроса, поэтому чужого
   ученика или чужое занятие нельзя запросить даже вручную.

Проверки в `server/domain/access.js` записаны как возможности (`canManageLessons`,
`canViewFinance`, `canAssignTeacher`…), а не как сравнение с ролью: четвёртая роль
потребует правки одного этого файла, а не двух десятков обработчиков. Те же флаги
уезжают в браузер (`window.PC.permissions`) и решают, какие кнопки показать, —
но это лишь отражение серверных правил, API проверяет права заново.

Заблокированный сотрудник теряет доступ немедленно: право проверяется по свежей записи
из `data/users.json`, а не по содержимому cookie.

## Модули

**Главная.** У администратора — ученики, заявки за период, преподаватели, оборот, занятия,
разрезы по направлениям и статусам. У преподавателя — ближайшее занятие с кнопкой
«Подключиться», список занятий без отметки об итоге и своя статистика.

**Заявки** (администратор и управляющий). Воронка `Новая → В обработке → Назначено вводное →
Ученик зачислен / Отказ`, поиск (в том числе по телефону без учёта формата), фильтры по дате
и статусу, история изменений по каждой заявке, выгрузка в CSV. Кнопка «В ученики» переносит
данные в новую карточку; статус «Ученик зачислен» иначе поставить нельзя — так заявка
и карточка не расходятся. О новой заявке администраторы узнают из колокольчика в шапке.

**Ученики.** Карточка: имя и возраст, направление, группа, преподаватель, особенности
(темп, поведение, здоровье, пожелания), статус, посещаемость и прогресс — это видят обе роли.
ФИО и контакты родителей, история оплат и заметки администратора — только администратор.
Фильтры по направлению, преподавателю, группе, статусу и возрасту, счётчики по направлениям,
история изменений карточки с указанием, кто и что поменял. Список групп в фильтре не задан
заранее — он собирается из фактических значений поля «группа» и сортируется по-человечески
(«Группа 2» идёт перед «Группой 10»). Выбранная группа запоминается и переживает
перезагрузку страницы и возврат из карточки ученика.

**Сотрудники** (только администратор). Создание учётной записи с логином и паролем,
блокировка, смена пароля, направления, список закреплённых учеников и статистика занятий.
Денег у сотрудника два вида: ставка за одно проведённое занятие и оклад за период —
фиксированная сумма, из которой складывается начисление у тех, кто занятий не ведёт
(администратор, управляющий). Последнего активного администратора система не даст
ни разжаловать, ни заблокировать. Адреса раздела остались прежними (`/app/teachers`) —
переименована подпись в меню, а не маршруты.

**Расписание.** Администратор и управляющий: календарь день / неделя / месяц, создание занятий,
в том числе повторяющихся (дни недели + дата окончания, до 200 занятий за раз), перенос,
удаление занятия или всей серии. У занятия есть поле «группа»: выбор группы в форме сразу
отмечает её учеников в списке состава — состав при этом остаётся редактируемым вручную. Преподаватель: виды день и неделя, только свои занятия, отметка
«проведено / отменено / перенесено», комментарий по итогам и посещаемость каждого ученика.
О любом изменении расписания преподаватель получает уведомление.

**Финансы** (администратор и управляющий). Оборот за период, оплаты учеников, расходы, график
доходов и расходов, отчёт по занятиям в разрезе преподавателей. Начисление считается
автоматически — ставка × число проведённых занятий за период плюс оклад; кнопка «Начислить»
превращает расчёт в запись расхода, повторно за тот же период начислить нельзя. В таблице
начислений есть все сотрудники, а не только преподаватели: у администратора и управляющего
занятий нет, и начисление им идёт окладом.

Оклад — величина месячная: он входит в начисление, только когда период выбран ровно
одним календарным месяцем (01-е — последнее число), и второй раз за тот же месяц
не начисляется, как бы ни двигали границы периода. Иначе оклад выплачивался бы дважды —
за 01–15 и за 16–31 августа. Занятия по ставке считаются за любой отрезок.

Чужая зарплата закрыта от управляющего: в расчёте он видит только преподавателей,
а начислить оклад администратору или другому управляющему ему отвечают `403`. Правила
и проверка — в `server/domain/payroll.js` и `server/routes/api/finance.js`, покрыты
тестами `tests/finance.test.js`.

## Команды

| Команда | Что делает |
|---|---|
| `npm start` | Запускает сервер на порту 3000 |
| `npm run dev` | То же, но перезапускается при правках файлов сервера |
| `npm run css` | Собирает Tailwind в `public/css/styles.css` |
| `npm run css:watch` | Пересобирает стили на лету — держите запущенным, пока правите вёрстку |
| `npm run seed` | Добавляет демо-данные ко всем модулям. Если они уже есть — ничего не создаёт и скажет об этом |
| `npm run seed:reset` | Очищает рабочие данные (кроме учётных записей) и создаёт демо заново |
| `npm run seed:sqlite` | То же, что `npm run seed`, но всегда в `data/app.sqlite`, независимо от `DATABASE_ENGINE` в `.env` |
| `npm run migrate:sqlite` | Разовый перенос данных из `data/*.json` в `data/app.sqlite` (см. «Хранение данных») |
| `npm run users` | Показывает список сотрудников |
| `npm run user:add -- <логин> <пароль>` | Создаёт администратора или меняет ему пароль. Роль задаётся флагом: `--manager`, `--teacher` или `--role <id>` |
| `npm run backup` | Резервная копия папки `data/` в `backups/backup_ГГГГММДД_ЧЧММСС.zip` (см. «Резервные копии») |
| `npm run restore <имя>` | Восстановление данных из копии. **Сервер должен быть остановлен** |

> **Важно:** после любой правки классов в HTML или в клиентском JavaScript запустите `npm run css`.
> Tailwind собирает только те классы, которые нашёл в исходниках, — иначе новые стили не появятся.

## Как проверить систему под разными ролями

1. `npm run seed:reset` — чистые демо-данные и три преподавателя.
2. `npm start`, открыть <http://localhost:3000/login>.
3. **Под администратором** (`Yarichpek375` или своя учётка):
   - на «Главной» видны все шесть плиток и оборот;
   - в «Заявках» откройте любую, поменяйте статус, нажмите «В ученики»;
   - в «Учениках» откройте карточку — видны родители, оплаты и история;
   - в «Расписании» нажмите «Новое занятие», включите «Повторять еженедельно»;
   - в «Финансах» нажмите «Начислить» напротив преподавателя.
4. Выйдите и войдите **под преподавателем** (`orlova` / `demo12345`):
   - в меню только «Главная», «Ученики», «Расписание», «Профиль»;
   - в списке учеников — трое, а не десять;
   - в карточке ученика нет блоков «Родители и контакты», «История оплат» и кнопки
     «Редактировать»;
   - в «Расписании» нет кнопки «Новое занятие» и вида «Месяц»; в окне занятия доступны
     только итог, комментарий и посещаемость;
   - в «Профиле» нет строк со ставкой и окладом.
5. Проверка «в лоб», без интерфейса — прямые запросы к API должны отвечать `403`:

```bash
# войти преподавателем и сохранить cookie
curl -c t.cookie -X POST http://localhost:3000/login \
  -H "Content-Type: application/json" \
  -d '{"login":"orlova","password":"demo12345"}'

curl -b t.cookie http://localhost:3000/app/api/applications      # 403
curl -b t.cookie http://localhost:3000/app/api/finance/summary   # 403
curl -b t.cookie http://localhost:3000/app/api/teachers          # 403
```

## Хранение данных

Движок хранения выбирается переменной `DATABASE_ENGINE` в `.env` — `sqlite` (по умолчанию)
или `json`. Модели, роуты и контроллеры о выборе движка не знают: программный интерфейс
`server/db.js` (`collection()`, `transaction()`) у обоих один и тот же.

**`sqlite`** (по умолчанию) — все коллекции лежат в одной базе `data/app.sqlite`
(путь настраивается через `SQLITE_STORAGE`). Каждая коллекция — своя таблица
`(id TEXT PRIMARY KEY, data TEXT)`, запись целиком — документом. Транзакции по нескольким
коллекциям (`db.transaction(['имя', …], fn)`) идут одним `BEGIN…COMMIT`: при ошибке внутри
`fn` откатываются сразу все участвующие коллекции, а не только текущий файл.

**`json`** — прежнее файловое хранилище, оставлено как запасной вариант (например, если на
сервере не собирается нативный драйвер `better-sqlite3`). Каждая коллекция — отдельный
JSON-файл в `data/`:

| Файл | Что внутри |
|---|---|
| `users.json` | сотрудники: логин, роль, ФИО, контакты, направления, ставка, оклад, доступ |
| `applications.json` | заявки с сайта, статус, комментарии менеджера, история |
| `students.json` | карточки учеников, включая данные родителей |
| `lessons.json` | занятия: дата, время, преподаватель, ученики, формат, ссылка, итог, посещаемость |
| `payments.json` | оплаты учеников |
| `expenses.json` | расходы, включая начисления преподавателям |
| `notifications.json` | уведомления в интерфейсе |
| `audit.json` | история изменений карточек и учётных записей |

Запись атомарная (временный файл + переименование), повреждённый файл не роняет сервер —
он откладывается рядом как `<имя>.corrupt-<дата>.json`, работа продолжается с пустым списком.
Файлы можно открыть и отредактировать вручную — сервер подхватит правки без перезапуска.
Транзакции по нескольким коллекциям здесь атомарны только на уровне одного файла за раз —
если диск откажет между записями, часть изменений уцелеет (в `sqlite` это устранено).

Изменяющие операции обоих движков выстроены в единую промис-очередь — параллельные запросы
не затирают друг друга.

**Перенос данных из `json` в `sqlite`**: `npm run migrate:sqlite` читает текущие `data/*.json`
и переносит их в `data/app.sqlite` через ту же нормализацию, что и приложение, сверяя число
записей после переноса. Исходные JSON-файлы при этом не изменяются и не удаляются — держите
их как резервную копию до тех пор, пока не убедитесь, что sqlite-версия работает как надо.
Откат — просто верните `DATABASE_ENGINE=json` в `.env`, файлы никуда не делись.

При первом запуске старые записи первой версии проекта обновляются автоматически: учётные
записи получают идентификаторы и роль «Администратор», заявки — статусы новой воронки
(`Думает`, `Перезвонить`, `Недозвон` → `В обработке`; `Согласился` → `Назначено вводное`).

## Резервные копии

Всё, что накопила школа, лежит в папке `data/`. Копию делает `npm run backup`,
возвращает данные `npm run restore`. Обе команды работают с папкой целиком: база,
JSON-коллекции, карантинные файлы, вложенные папки — что лежит в `data/`, то и в копии.

### Создать копию

```bash
npm run backup
```

Копия появится в `backups/` с датой и временем в имени:

```
  Снимок базы данных:
    app.sqlite                   онлайн-снимок, 216.0 КБ
    записей в снимке: 258 (applications 19, audit 24, expenses 8, lessons 128, …)

  Упаковка файлов:
    data/app.sqlite                      216.0 КБ → 19.5 КБ
    data/applications.json                13.1 КБ → 2.1 КБ
    …
  Проверка архива…
    записей: 10, контрольные суммы совпали

  ✓ Бэкап создан
    D:\ProCode\backups\backup_20260801_185807.zip
    файлов: 9, исходный объём: 365.7 КБ, на диске: 33.2 КБ
```

Строка «записей в снимке» — не украшение, а способ проверить копию глазами: числа должны
совпадать с тем, что видно в платформе. Сразу после записи архив перечитывается и у каждого
файла сверяется контрольная сумма — про испорченную копию вы узнаете сейчас, а не в день аварии.

**Сервер останавливать не нужно.** База снимается штатным механизмом SQLite, который отдаёт
согласованное состояние даже под нагрузкой, а JSON-файлы пишутся атомарно.

Архив — обычный ZIP, открывается Проводником, WinRAR, 7-Zip. Внутри:

```
manifest.json          опись: когда снято, чем, сколько файлов, сколько записей в базе
data/app.sqlite        снимок базы
data/applications.json
data/students.json
…                      и всё остальное содержимое папки data/
```

Флаги передавайте после `--` — иначе npm заберёт их себе:

| Команда | Что делает |
|---|---|
| `npm run backup -- --dir` | Копия обычной папкой, без архива — если её потом смотреть без распаковщика |
| `npm run backup -- --out D:\Backups\ПроКод` | Сложить копию в другое место, например на внешний диск |
| `npm run backup -- --wait 60` | Ждать до 60 секунд, если данные заняты другой служебной командой |
| `npm run backup -- --force` | Снять чужую блокировку принудительно (см. ниже) |
| `npm run backup -- --help` | Подсказка по флагам |

> **Почему база не просто копируется.** SQLite работает в режиме WAL: свежие изменения
> лежат не в `app.sqlite`, а в журнале `app.sqlite-wal` рядом. На момент написания этих строк
> сама база весила 217 КБ, а журнал — 828 КБ. Копия одного `app.sqlite` потеряла бы бо́льшую
> часть данных. Поэтому скрипт делает *снимок*: SQLite собирает базу и журнал в один цельный
> файл, и в архив идёт он. Файлы `-wal` и `-shm` в архив намеренно не кладутся — рядом
> со снимком они бессмысленны и при восстановлении только испортили бы базу.

> **Побочный эффект.** Чтобы снять базу, скрипт её открывает и закрывает. Если сервер в этот
> момент не работает, SQLite при закрытии переносит журнал в основной файл и удаляет
> `app.sqlite-wal` и `app.sqlite-shm`. Это нормально — ровно то же делает корректно
> остановленный сервер. Данные не теряются, `app.sqlite` просто становится больше.

### Восстановить данные

**Сначала остановите сервер** (`Ctrl + C` в его окне). Подменить файл базы под работающим
процессом — надёжный способ испортить данные, и никакие проверки скрипта от этого не спасут.

```bash
npm run restore backup_20260801_185807.zip
```

Имя можно писать без расширения (`backup_20260801_185807`) или указывать путь к файлу
где угодно на диске. Забыли имя — запустите `npm run restore` без аргумента, скрипт покажет
список доступных копий.

Дальше всё происходит в строгом порядке, и **оригиналы трогаются только на четвёртом шаге**:

1. **Распаковка во временную папку.** У каждого файла сверяется контрольная сумма. Битый архив
   останавливает восстановление здесь — рабочие данные ещё не тронуты.
2. **Проверка содержимого.** База проверяется на целостность (`PRAGMA integrity_check`),
   сверяется наличие таблиц, каждый JSON разбирается и проверяется, что это список записей.
   Любая неудача — отказ, `data/` остаётся как была.
3. **Проверка движка хранения.** Движок, на котором снята копия, сверяется с текущим
   `DATABASE_ENGINE` — см. врезку ниже. Не совпал — отказ, `data/` остаётся как была.
4. **Замена.** Текущее содержимое `data/` сначала целиком копируется в откатную копию,
   и только потом заменяется. Если что-то пойдёт не так — автоматический откат.
5. **Контрольное чтение.** Скрипт открывает уже восстановленную базу и печатает, что в ней
   получилось:

```
  Данные в базе app.sqlite:
    Заявки                 19
    Журнал действий        24
    Расходы                 8
    Занятия               128
    Уведомления            22
    Платежи                32
    Ученики                20
    Сотрудники              5   (администраторов: 2, преподавателей: 3)

  ✓ Восстановление завершено
    Запустите сервер: npm start
```

Сверьте цифры с тем, чего ожидали, и запускайте сервер.

> **Замена идёт целиком.** Всё содержимое `data/` заменяется содержимым копии — это
> осознанно. Иначе рядом с восстановленной базой остался бы её старый журнал `-wal`,
> и SQLite при первом открытии применил бы его поверх восстановленных данных: получилась бы
> смесь двух состояний. Ничего не пропадает — см. следующий пункт.

> **Копия из-под другого движка не восстанавливается.** Движки не читают данные друг друга:
> `sqlite` берёт записи только из `data/app.sqlite`, `json` — только из `data/*.json`.
> Восстановить старую копию, снятую при `DATABASE_ENGINE=json`, в проект на `sqlite` —
> значит удалить рабочую базу и положить на её место файлы, которых сервер не увидит:
> при следующем `npm start` SQLite создала бы новую пустую базу, а команда отчиталась бы
> об успехе. Поэтому скрипт сверяет движок из описи копии с текущим `DATABASE_ENGINE`
> и отказывается работать до замены данных. Копии, снятые до появления этой проверки,
> описи с движком не содержат — для них скрипт смотрит по содержимому: есть ли в копии
> то, что текущий движок вообще умеет читать.
>
> Что делать при отказе: либо вернуть `DATABASE_ENGINE` под копию (для `json` → `sqlite`
> после восстановления пригодится `npm run migrate:sqlite`), либо, если вы понимаете
> последствия, повторить с флагом `npm run restore <имя> -- --ignore-engine` — он отключает
> только эту проверку и ничего не конвертирует. Такое восстановление и заканчивается не
> «✓ Восстановление завершено», а предупреждением: файлы на месте, но сервер их не прочитает,
> и запускать его до приведения данных и `DATABASE_ENGINE` в соответствие нельзя.

### Куда девается то, что было до восстановления

Перед заменой скрипт складывает текущее состояние `data/` в `backups/prerestore_<дата>_<время>/`
и говорит об этом в конце работы. Это ваша страховка: восстановили не ту копию — верните файлы
из этой папки обратно в `data/` вручную.

Автоматически такие папки не удаляются никогда, в том числе очисткой `--prune`.
Убедились, что всё на месте — удалите их сами.

### Очистка старых копий

Копии накапливаются и **по умолчанию не удаляются**. Убрать старые можно только явной командой:

```bash
npm run restore backup_20260801_185807.zip -- --prune --keep 5
```

Останется 5 самых свежих. Копия, из которой только что восстановились, не удаляется никогда,
даже если она старше лимита. Папки `prerestore_*` очистка не трогает.

### Если данные заняты

На время работы обе команды создают файл-флаг `data/app.sqlite.lock` — чтобы бэкап
и восстановление не столкнулись друг с другом. Увидели сообщение «Хранилище заблокировано» —
значит, рядом уже работает такая же команда.

- Подождать дольше: `npm run backup -- --wait 60`
- Флаг остался от аварийно завершённого запуска — скрипт заметит это сам (процесса нет
  или файл старый) и перехватит блокировку с предупреждением.
- Совсем уверены, что процесса нет: `npm run backup -- --force`

Флаг **рекомендательный**: он разводит между собой только `backup` и `restore`. Работающий
сервер про него не знает и продолжает писать в базу — поэтому восстановление и требует
остановленного сервера.

### По расписанию

Бэкап — обычная консольная команда, её удобно повесить на планировщик. Windows: положите
рядом с проектом файл `backup.cmd`

```bat
@echo off
cd /d D:\ProCode
call npm run backup
```

и добавьте задачу в «Планировщик заданий» (ежедневно, например в 03:00). На Linux-сервере —
строка в `crontab -e`:

```
0 3 * * * cd /srv/prokod && /usr/bin/npm run backup >> /var/log/prokod-backup.log 2>&1
```

Путь к `npm` в планировщике лучше указывать полный: `PATH` у службы отличается от вашего.

Копии по расписанию имеет смысл складывать не на тот же диск, что и проект — например,
`npm run backup -- --out E:\Backups\ПроКод`, а оттуда синхронизировать в облако.

### Чего в копии нет

Копируется **только `data/`**. Настройки `.env` в архив не попадают намеренно: там пароли
и секрет сессии, и держать их копию в незашифрованном ZIP рядом с проектом — плохая идея.
Сохраните `.env` отдельно и надёжно. Код, стили и `node_modules` восстанавливаются из
репозитория и `npm install`, копировать их незачем.

Папка `backups/` добавлена в `.gitignore` — резервные копии не попадут в репозиторий.

## Как работают заявки

1. Родитель заполняет форму в конце лендинга.
2. `public/js/form.js` проверяет поля и отправляет `POST /api/applications`.
3. Сервер **заново проверяет всё сам** (клиенту не доверяем), нормализует телефон
   к виду `+7XXXXXXXXXX` и дописывает заявку в `data/applications.json`.
4. Заявка появляется в модуле «Заявки» со статусом «Новая», все администраторы получают
   уведомление, а обращение печатается в консоль сервера — так вы увидите его, даже не заходя
   в платформу.

## Учётные записи

Сотрудники хранятся в `data/users.json`. **Паролей в этом файле нет** — для каждого лежит
случайная соль и scrypt-хэш, из которого пароль обратно не достаётся. Файл добавлен
в `.gitignore`, чтобы не попасть в репозиторий.

Сотрудников удобнее заводить в интерфейсе: **Сотрудники → Новый сотрудник**.
Из командной строки доступно то же самое:

```bash
npm run users                                              # кто заведён
npm run user:add -- ivan МойПароль123                      # администратор
node scripts/manage-users.js --add masha Пароль123 --teacher --name "Мария Орлова"
node scripts/manage-users.js --remove ivan                 # удалить
```

Удаление ведёт себя так же, как в интерфейсе: ученики открепляются от сотрудника,
его уведомления удаляются, а при наличии запланированных занятий команда откажется
работать — чтобы расписание не осталось с ссылками в никуда. Так же команда откажется
удалять единственного активного администратора: без него в систему станет некому войти.
Снять обе проверки можно флагом `--force`.

Пароль можно не писать в командной строке — он попадает в историю оболочки. Надёжнее
передать его через стандартный ввод:

```bash
echo "МойПароль123" | node scripts/manage-users.js --add ivan
```

Полезно знать:

- Логин сравнивается **без учёта регистра**, пароль — с учётом.
- Проверка пароля намеренно занимает около 50 мс: это делает перебор бессмысленным
  и незаметно для человека.
- Удалили или заблокировали сотрудника — его открытые сессии перестают действовать сразу.
- Пока `data/users.json` пуст или отсутствует, вход работает по `ADMIN_LOGIN` и `ADMIN_PASSWORD`
  из `.env`. **Как только заведён хотя бы один сотрудник, этот запасной вход отключается** —
  сейчас он уже не работает.
- Один сеанс живёт 12 часов, дальше нужно войти заново.
- Восемь неудачных попыток входа с одного адреса блокируют вход на 15 минут.

## Настройка

Все настройки — в файле `.env` в корне проекта:

```ini
PORT=3000
ADMIN_LOGIN=admin
ADMIN_PASSWORD=procode2025
SESSION_SECRET=<длинная случайная строка>
DATABASE_ENGINE=sqlite
SQLITE_STORAGE=data/app.sqlite
TZ=Europe/Moscow
TRUST_PROXY=0
```

- **`DATABASE_ENGINE`** — `sqlite` (по умолчанию) или `json`, см. «Хранение данных».
- **`SQLITE_STORAGE`** — путь к файлу базы SQLite. Относительный путь считается от корня проекта.
- **`ADMIN_LOGIN` и `ADMIN_PASSWORD`** — запасной вход на случай, если `data/users.json` пуст.
  Сейчас заведены учётные записи, поэтому эти значения не используются. Сервер всё ещё
  предупреждает о стандартном пароле при запуске — лучше задать здесь свой: он понадобится,
  если файл учётных записей будет потерян.
- **`SESSION_SECRET`** — секрет для подписи cookie. Если его удалить, после каждого перезапуска
  придётся входить заново.
  Сгенерировать новый: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`
- **`TZ`** — часовой пояс, в котором сервер считает «сегодня», «эту неделю» и «этот месяц».
  От него зависят цифры дашборда, подсветка текущего дня в расписании и периоды начислений.
  Без строки берётся `Europe/Moscow`; на VPS и в Docker по умолчанию UTC, поэтому пояс лучше
  задать явно. Название пояса печатается при запуске сервера — там его и стоит проверить.
- **`TRUST_PROXY`** — ставьте `1`, только если сайт стоит за nginx или Caddy. Иначе
  ограничения по IP можно будет обойти подделкой заголовка.

После правки `.env` перезапустите сервер.

## Публикация на сервере

Проект — обычное Node-приложение, разворачивается на любом VPS:

1. Скопируйте файлы, выполните `npm install --omit=dev` и `npm run css`.
2. Создайте `.env` с рабочим паролем, секретом и часовым поясом (`TZ=Europe/Moscow`).
3. Поднимите процесс через `pm2`, `systemd` или Docker.
4. Поставьте перед ним nginx с HTTPS и укажите `TRUST_PROXY=1`. Если на прокси включено
   своё сжатие, уберите `compression` из `server/index.js` — дважды сжимать ответ незачем.
5. Настройте резервное копирование папки `data/` — это единственное место, где живут
   заявки, ученики, расписание и финансы. Для этого есть `npm run backup`: повесьте его
   на `cron` и складывайте копии на другой диск или в облако — см. раздел
   [«Резервные копии»](#резервные-копии). Файл `.env` в копию не попадает, сохраните
   его отдельно.

## Технические решения

- **Node.js + Express**, зависимостей всего две: сам Express и `compression` для gzip.
  Авторизация, разбор cookie и парсер `.env` написаны на стандартной библиотеке, чтобы
  не тащить лишнее. Графики в финансах нарисованы обычным SVG, без библиотек.
- **Сжатие ответов** включено в приложении (`compression`): без него `styles.css` уезжает
  клиенту на 65 КБ, а HTML главной — на 110 КБ. Если сайт стоит за nginx, сжатие лучше
  делать на прокси (`gzip on` / `brotli on`), а middleware в `server/index.js` убрать:
  один и тот же ответ незачем сжимать дважды.
- **Хранилище — JSON-файлы** через общий движок `server/db.js`. Этого достаточно для школы
  на несколько сотен учеников. Дальше стоит перейти на SQLite: менять придётся только `db.js`.
- **Разграничение прав в одном месте** — `server/domain/access.js`. Там же сериализаторы,
  которые вырезают лишние поля из ответа. Интерфейс не «прячет» данные, их просто нет.
- **Страницы платформы собираются на сервере** по роли, данные подгружает браузер через
  `/app/api/*`. Меню преподавателя не содержит ссылок на закрытые разделы даже в исходном коде.
- **Tailwind CSS 3** со своей дизайн-системой в `src/input.css`: чернильно-синий `#0F1222`,
  кобальт `#2B4BF2`, тёплый абрикосовый акцент `#FF9E64`. Шрифты — Unbounded (заголовки),
  Onest (текст), JetBrains Mono (цифры и код).
- **Защита:** серверная валидация всех полей, ловушка для ботов, блокировка перебора пароля,
  подписанная HttpOnly-cookie с `SameSite=Lax`, проверка заголовка `Origin` на изменяющих
  запросах, сравнение секретов за постоянное время, экранирование формул при выгрузке в CSV,
  заголовки `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`
  и `Referrer-Policy`. Данные попадают в интерфейс только через `textContent` — внедрить
  скрипт через заявку или комментарий нельзя. Ссылки на созвон принимаются только с `http(s)`.
- **CSP без `unsafe-inline`** (`server/csp.js`): единственный инлайновый скрипт платформы
  получает одноразовый `nonce`, микроразметка лендинга разрешена по sha256-хэшам, которые
  считаются при старте сервера. Поправили инлайновый блок в `public/index.html` —
  перезапустите сервер, иначе браузер его заблокирует.
- **Ограничители частоты.** Вход: 8 неудачных попыток за 15 минут с одного IP.
  Форма заявки: 5 успешных заявок и 30 любых обращений за 10 минут с одного IP.
  Внутреннее API `/app/api/*`: 300 запросов и из них не больше 90 изменяющих за 5 минут
  на сотрудника (для не вошедших — на IP).
- **Кэширование.** HTML — всегда `no-cache`. Ссылки на CSS и JS внутри разметки несут метку
  версии (`?v=<8 hex-символов sha256 от содержимого>`), и файл с верной меткой отдаётся
  с `public, max-age=31536000, immutable`; без метки или с устаревшей — прежний `no-cache`
  с ревалидацией по ETag. Картинки и шрифты — на час. Страницы платформы и ответы её API —
  `no-store, private`: в них данные сессии, сохранять их нельзя ни браузеру, ни прокси.
- **Доступность:** страницы работают с клавиатуры, у элементов видимый фокус, модальные окна
  запирают фокус внутри и закрываются по `Esc`, анимации отключаются при системной настройке
  «уменьшить движение».

## Известные ограничения

- Уведомления живут только внутри интерфейса: почта и мессенджеры не подключены, для этого
  нужны сторонние сервисы и ключи. Страница опрашивает сервер раз в 30 секунд.
- Счётчики ограничения частоты и неудачных входов живут в памяти: после перезапуска сервера
  обнуляются.
- Отдельной сущности «группа» нет: у ученика есть текстовое поле «группа», а занятие просто
  ссылается на нескольких учеников. Для школы такого размера этого достаточно.
- Удаление безвозвратное, «корзины» нет (перед удалением спрашивается подтверждение).
  Вместе с карточкой ученика удаляются его оплаты, и он убирается из всех занятий,
  а заявка, из которой карточку завели, возвращается в статус «В обработке» — её снова
  можно сконвертировать. Пока карточка жива, заявку не удалить и её статус не поменять:
  статус ученика меняется в самой карточке.
- Вёрстка проверена в браузере на движке Chromium при ширинах 390–1440 px, горизонтальной
  прокрутки нет. Диапазон 320–390 px стоит один раз просмотреть глазами на реальном телефоне.
- Список заявок отдаётся не целиком: показываются свежие 200 из подошедших под фильтр,
  под таблицей об этом написано прямо. Заявки — единственная коллекция, которая растёт
  без конца, поэтому у неё есть потолок; остальные ограничены либо размером школы,
  либо в моделях (история — 50 записей, уведомления — 30). Полноценной пагинации
  со страницами нет: старые заявки ищутся поиском и фильтром по датам, а забрать
  вообще всё можно выгрузкой в CSV — она не обрезается.
- Версионирование статики покрывает только то, на что есть ссылки в разметке
  (`server/assets.js` проставляет `?v=<хэш содержимого>` при старте процесса).
  Модули платформы — нативные ES-модули с относительными импортами: запрос-строка
  на импорты не переносится, поэтому метку получает только точка входа
  `<script type="module">`, а её зависимости продолжают ревалидироваться по ETag.
  Подставлять версии внутрь самих файлов — работа сборщика, которого в проекте нет.
  Белого экрана после деплоя это не возвращает: ревалидация гарантирует свежесть,
  метка лишь снимает лишние запросы.
